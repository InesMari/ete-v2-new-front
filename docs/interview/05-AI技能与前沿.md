## 5-1. 你在项目里用 AI 做了什么？效果如何？（★★★）

**详细回答（口述稿）：**
> "我在公司主导了 AI 应用落地，做了两件事。第一件是知识库问答：把物流业务的文档（运单规则、常见问题、政策条款）整理进知识库，用 Dify 做 RAG 检索 + 通义千问生成，前端做了 aiChat 聊天组件，支持流式输出和多会话，员工问'运输破损怎么理赔'能直接得到基于公司规则的准确答复，替代了翻文档。第二件是智能调度探索：这是把 AI 接进真实业务流程——给 AI 一批订单，让它按规则输出调度建议，但关键是我们约束它输出结构化 JSON，前端解析后回填到调度表单，人工确认后执行，形成'AI 出方案、人拍板、系统执行'的闭环，而不是聊天玩具。效果上：知识库问答把客服/运营查规则的效率提升了，智能调度完成了 POC 验证。我的总结：AI 落地最难的不是技术，是'让 AI 的输出能对接进现有系统'，这个闭环是真正的价值点。"

**答案要点：**
- 两条线：
  1. **知识库问答**：物流业务规则（运费计算、丢损赔付、操作规范）沉淀为知识库，司机/客服自助问答，减少人工咨询。
  2. **智能调度 Demo**：AI 理解自然语言 → 结构化 JSON → 前端执行业务接口（查订单/派单）→ 结果回填对话，形成"AI 助手操作业务系统"的闭环。
- 技术栈：Dify（工作流编排 + 知识库管理）+ 通义千问/DeepSeek（模型）+ Vue3 前端组件（流式对话）。
- 效果（能量化就量化）：客服高频问题自助解答率、新司机培训咨询量下降等；Demo 已跑通"语音/文本 → 业务操作"闭环。
- 架构图（面试画一遍）：
  `用户 → 前端(aiChat组件) → LLM/Agent → 工具调用(白名单接口) → 业务系统 → 结果回填`

**【项目案例】** 引用 `aiChat.js`：`createProvider('dify')` 用 Dify 对话 API + `conversation_id` 保持上下文；`agentRouter` 解析 AI 输出执行工具调用。这是简历中最有区分度的部分，**优先讲，主动讲**。

## 5-2. 什么是 RAG？为什么用它而不是让大模型直接回答？（★★★）

**详细回答（口述稿）：**
> "RAG 就是检索增强生成，四步走：把私有文档切块 → 向量化（Embedding）存进向量库 → 用户提问时把问题也向量化去检索最相关的片段 → 把片段拼进 Prompt 给大模型，让它'基于提供的资料回答'。为什么不用大模型直接答？两个致命问题：一是知识实时性，模型训练数据是历史的，公司内部文档它根本没见过；二是幻觉，模型不懂的它会一本正经地编。RAG 把'答案的来源'从模型参数变成'可检索的资料'，回答有出处、可追溯、可更新——文档更新后重跑索引就行，不用重训模型。项目里我们把物流知识文档切块后建了知识库，回答时先检索再生成，还能附上来源。跟微调比：RAG 适合'知识经常变、需要可解释'的场景，微调适合'风格和专有能力'。我总结：RAG 是私有知识注入大模型性价比最高的方式。"

**答案要点：**
- RAG（Retrieval-Augmented Generation）：检索增强生成。流程：用户问题 → 向量化 → 知识库检索 TopK → 拼进 Prompt → LLM 基于检索内容回答。
- 为什么用 RAG：
  1. **抗幻觉**：答案有知识库出处约束。
  2. **知识实时更新**：改文档即可，不用重训模型。
  3. **数据私有/合规**：企业数据不出域，模型只做推理。
  4. **成本低**：比微调便宜。
- 核心组件：文档解析 → 切分（chunk）→ 向量化（Embedding）→ 向量库（Milvus/Chroma/PGVector）→ 检索（相似度 + 重排 rerank）→ 生成。
- 与微调对比：微调改"模型行为/风格"，RAG 补"事实知识"；两者可组合。

**【项目案例】** 物流知识库的坑：直接把整本《运费规则 PDF》丢进向量库，检索命中率低。优化：①按条款结构化切分（标题 + 条款号作为元数据）②切分大小调优（256~512 token + 重叠）③检索后加 rerank 重排 ④答案强制引用条款编号。**"切分质量决定问答质量"**是实战者才知道的结论。

## 5-3. 什么是 Prompt Engineering？你有哪些实用技巧？（★★）

**详细回答（口述稿）：**
> "Prompt Engineering 是设计提示词引导大模型输出的工程方法，我常用的技巧按场景讲。一是角色设定，'你是一名物流调度专家'让输出更专业；二是给示例（Few-shot），给一两个输入输出对，比描述规则更准；三是结构化输出约束，明确说'输出 JSON，字段为 xxx'，配合系统层的 JSON mode 更稳；四是拆任务，复杂问题拆成多步工作流，Dify 里就是编排节点；五是给约束条件，'只用提供的资料回答、不知道就说不知道'，有效减少幻觉；六是 COT 思维链，让模型'先分析再给结论'，提高复杂推理准确率。项目里知识库问答的 Prompt 就是'角色 + 资料约束 + 引用来源'的组合。我总结：Prompt 不是玄学，本质是'把需求表达清楚'，技巧在输出端的约束和示例上最见效。"

**答案要点：**
- 定义：设计输入指令让模型稳定输出期望结果；本质是与模型"对齐"。
- 核心技巧：
  1. **角色设定**：`你是一个物流客服助手，回答只基于给定知识库`。
  2. **结构化约束**：指定输出格式（JSON schema / Markdown 表格 / 枚举值），配合 5-6 的 JSON mode。
  3. **少样本（Few-shot）**：给 2-3 个输入输出示例，大幅提升格式稳定性。
  4. **边界约束**：明确"不知道就说不知道""只做查询不做删除"。
  5. **思维链（CoT）**：复杂计算/多条件判断让模型"分步骤思考"。
  6. **温度控制**：事实问答温度低（0.2~0.3），创意内容温度高。
- 迭代方法：基线 Prompt → 测试集（20-50 条典型问题）→ 对比输出 → 迭代；Prompt 也要版本管理（存 Dify/配置文件）。

**【项目案例】** 智能调度 Prompt 骨架（可现场背）：
```
你是物流调度助手。任务：把用户意图转为工具调用。
可选工具：{queryOrderInfoList, saveDispatch, queryVehicleInfoPage}
规则：1)只调用白名单工具 2)参数必须来自对话 3)缺少必填参数时提问，不要猜。
输出严格 JSON：{"tool":"...","params":{...}}
```
配合白名单接口 + 人工确认，是"可控 Agent"的落地方案。

## 5-4. Dify 平台你用到什么程度？（★★）

**详细回答（口述稿）：**
> "Dify 我按能力层次讲用到什么程度。基础层：知识库管理——文档切块、向量化、召回测试，这是日常用最多的；编排层：工作流编排——把'意图识别 → 知识检索 → 生成'串成可视化工作流，还接入了工具节点（调用我们的业务 API）；应用层：API 接入——前端不直接连模型，而是连 Dify 的应用 API，支持对话模式和 response_mode 流式；高级层：Agent 和工具调用——让 AI 能主动调我们后端接口查订单、算调度。我的用法心得：Dify 的价值是'把 AI 侧的工程问题（模型管理、检索、Prompt、成本）从前端剥离'，前端只需要对接一个标准 API。边界我也清楚：复杂业务逻辑和权限校验仍然在前端和后端，Dify 只负责'生成'这一层。这题我会主动画'前端 ↔ Dify ↔ 模型/知识库'的架构图，展示不是调个接口那么简单。"

**答案要点：**
- Dify = LLM 应用开发平台，可视化编排（工作流/Agent/知识库/对话应用）。
- 我用到的功能：
  1. **知识库管理**：文档上传、分段（chunk）、检索测试、引用设置。
  2. **工作流编排**：问题分类 → 意图路由 → 检索 → 生成 → 工具调用（HTTP 节点调业务接口）。
  3. **Agent 能力**：`conversation_id` 多轮上下文、工具节点。
  4. **API 接入**：对话应用暴露 OpenAI 兼容 API，前端 `POST /v1/chat-messages` + SSE 流式接收。
  5. **Prompt 管理**：应用内 Prompt 版本迭代、变量注入（用户信息）。
- 替代方案：LangChain（更底层、更重）；自建（成本高）。Dify 的价值是"降低 LLM 应用工程化门槛"。

**【项目案例】** 前端对接细节：`createProvider('dify')` 里封装 `fetch('/v1/chat-messages', { method:'POST', body: JSON.stringify({ inputs, query, conversation_id, response_mode:'streaming' }) })`，用 SSE 逐块解析 `data:` 行拼成 `streamingContent`；用 `conversationMap`（sessionId → conversation_id）让前端多会话与 Dify 会话一一对应。能讲出 `response_mode: 'streaming'` 和 `conversation_id` 这两个参数，就是真实用过 Dify 的铁证。

## 5-5. 流式输出（SSE）在前端怎么实现？（★★★）

**详细回答（口述稿）：**
> "流式输出就是让模型一个字一个字往外蹦，用户体验像打字机。技术底座是 SSE（Server-Sent Events）——基于 HTTP 的长连接，服务端可以持续推送文本流，`Content-Type: text/event-stream`，数据按 `data:` 分帧，结束用 `\n\n`。前端三种接法：原生 `EventSource` 最简单但只支持 GET；Fetch 读流更灵活——`response.body.getReader()` 拿 ReadableStream 循环读 chunk，按行解析拼接到内容；还有 axios 的 `onDownloadProgress`。三个工程细节：一是用 AbortController 支持'停止生成'；二是聊天消息要按会话隔离，切换会话要清理正在进行的流；三是网络中断要有重连或提示。项目里 aiChat 组件就是 Vue3 + Fetch 流式解析，边读边 `reactive` 更新内容，配合 nextTick 自动滚动，还实现了多会话管理和停止生成。答这题我会现场画'请求 → 分帧 → 解析 → 拼接 → 滚动'的链路。"

**答案要点：**
- 原理：服务端 `text/event-stream`，数据按 `data: xxx\n\n` 分块下发，`Content-Type: text/event-stream`，连接保持。
- 前端实现：
  1. `fetch` + `response.body.getReader()` 读流，`TextDecoder` 解码，按 `\n` 切分事件行解析。
  2. 或 `EventSource`（原生 SSE，但只支持 GET、不能自定义 header，常需 `fetch` 方案）。
  3. 边收边追加到 `streamingContent`，配合 `nextTick` 滚动到底部 + 打字机效果。
  4. **中断**：`AbortController.abort()` 停止请求与生成。
  5. **边界**：断流重连、空块过滤、JSON 截断时的容错（流式 JSON 解析用累积 buffer）。
- 与 WebSocket 对比：SSE 单向服务端推送、自动重连、HTTP 兼容性好；WebSocket 双向，适合聊天/游戏。

**【项目案例】** `aiChat.js` 的流式三要素：`isStreaming` 状态（控制发送按钮禁用/停止）、`streamingContent` 增量渲染（markdown 实时转换）、`playbackStopped`（停止播放后剩余流丢弃）；`typeDelay` 实现逐字打字机，让"流式 + 打字机 + 可停止"三个体验点一次到位。

## 5-6. 怎么约束大模型输出结构化 JSON？（★★）

**详细回答（口述稿）：**
> "约束结构化输出我从三层讲。第一层 Prompt 约束：明确给 JSON 模板和字段说明，'只输出 JSON，不要多余文字'，并给一个示例；第二层平台能力：Dify/OpenAI 都有 JSON mode 或结构化输出（response_format），声明 schema 后模型保证按结构返回；第三层代码兜底：解析用 try/catch，不是 JSON 或字段缺失时走降级——重新请求或提示用户。项目里智能调度就是典型：AI 收到订单列表后，输出 `{ "plan": [{ "orderId": ..., "vehicleId": ..., "remark": ... }] }` 这样的调度建议 JSON，前端 `JSON.parse` 后校验字段，回填到调度表单，人工确认再提交——所以 JSON 结构是和后端一起定死的 schema，不是我随手写的。还有两个细节：数字字段要注意模型可能输出字符串，解析后要显式 Number 转换；字段名用驼峰还是下划线要跟后端约定一致。"

**答案要点：**
- 为什么重要：AI 输出要交给前端/后端程序执行（工具调用、表单填充），非结构输出 = 程序崩。
- 手段（从硬到软）：
  1. **JSON mode**（OpenAI `response_format: {type:'json_object'}` / 通义 `enable_thinking` + 约束）：模型保证输出合法 JSON。
  2. **函数调用（Function Calling）**：定义 `tools` 的 JSON Schema，模型按 schema 填参数，最稳。
  3. **少样本 + 强约束 Prompt**：示例 + "只输出 JSON，不要解释"。
  4. **输出校验 + 重试**：前端/后端 `JSON.parse` + schema 校验（zod/json-schema），失败自动重试一次。
  5. **后处理兜底**：从 markdown 代码块中提取 JSON、正则修复常见格式错误。
- 注意：JSON 解析失败 ≠ 模型不行，往往是流式传输截断或 Prompt 漂移，校验 + 重试是标配。

**【项目案例】** 智能调度的"三段防线"：①Dify 工具节点按 schema 输出 ②前端 `agentRouter` 里 `JSON.parse` 失败自动重试 + 正则提取 ③`difyExecutor.registerDefaultInterfaces` 接口白名单，只有合法工具名才执行。面试讲"**宁可拒绝执行，不可错误执行**"的安全意识。

## 5-7. Token 成本怎么控制？（★★）

**详细回答（口述稿）：**
> "Token 成本控制我按'减量、降频、缓存'三个思路讲。减量：Prompt 精简——知识库检索只带回相关片段而不是全量文档，历史对话只保留最近的几轮（对话太多会超上下文而且费钱），输出端限制 max_tokens 防止模型长篇大论；降频：对高频的常见问题做命中缓存——Dify 有回答缓存，相同问题直接返回缓存结果；会话合并——把低频操作的用户问题做意图预筛，只有真正需要大模型的才调用；缓存：长 Prompt 用 KV Cache 复用，或把重复的静态内容（系统提示、公司背景）抽出来用平台的 prompt 缓存。项目里知识库问答默认 top_k 召回 3~5 段，历史窗口保留 10 轮，单次调用成本压到了几分钱量级。我总结：成本控制的核心是'让模型只做它必须做的活'，能检索解决的不生成、能缓存的不重复调用。"

**答案要点：**
- 成本模型：输入 token × 输入单价 + 输出 token × 输出单价（输出更贵）；Prompt 越长越贵，重复调用翻倍。
- 控制手段：
  1. **精简 Prompt**：去掉冗长指令、历史会话裁剪（只保留最近 N 轮 + 摘要）。
  2. **缓存**：相同问题命中缓存直接返回（对话级缓存 key = 用户+问题+知识库版本）。
  3. **模型分级**：简单问答用便宜小模型，复杂推理用强模型。
  4. **RAG 控制上下文**：只拼 TopK 检索片段，而不是整本知识库。
  5. **流式输出即到即用**：不缓存大输出；日志记录每会话 token 用量做预算。
  6. **额度治理**：用户每日限额、并发控制、超限降级（小模型/模板回复）。
- 度量：每次请求返回 `usage.prompt_tokens/completion_tokens`，记录到日志做成本报表。

**【项目案例】** 知识库问答的省钱方案：①问题先走"关键词意图分类"（便宜小模型），命中高频问题直接返回知识库原文（根本不调大模型）②语义检索 TopK 从 5 降到 3（答案质量几乎不变，输入 token 省 40%）③会话历史只保留最近 6 轮。**"预算敏感型 AI 应用"**是工程落地与炫技 Demo 的分水岭。

## 5-8. 向量检索是什么？Embedding 怎么选？（★★）

**详细回答（口述稿）：**
> "向量检索就是把文本转成高维向量（Embedding），语义相近的文本向量距离也近，查询时把问题转向量，用余弦相似度或内积找最近的片段。它比关键词检索强在'语义匹配'——搜'货丢了怎么办'能命中'运输途中货物遗失的处理流程'这种说法不同但语义相同的文档。Embedding 怎么选我给三个维度：一是语言适配，中文场景选中文效果好的模型（比如 BGE、通义的 text-embedding），英文模型对中文支持差；二是维度权衡，维度越高越准但存储和计算越大；三是跟平台集成，Dify 里配置了对应的 Embedding 模型后知识库才能用。工程细节：切块大小影响检索质量——块太大噪声多、块太小上下文不完整，我们按段落和语义切，每块几百字；top_k 和相似度阈值要调到'查得到又不乱返回'。我总结：RAG 的效果瓶颈往往不在生成，而在检索——Embedding 选型和切块策略决定上限。"

**答案要点：**
- Embedding：把文本映射成高维向量，语义相近 → 向量距离近（余弦相似度）。
- 向量检索流程：文档切块 → 每块 embedding → 存向量库 → 查询时把问题 embedding → TopK 相似度召回。
- 向量库选型：Milvus（大规模生产）、Chroma/pgvector（中小型）、FAISS（本地内存）；Dify 内置也可配外部。
- Embedding 模型选型：维度（1536/1024/768）、中文效果（bge-m3 / text-embedding-v3 / 通义）、成本与延迟；**同一套语料的 query 与 document 要同模型**。
- 检索效果优化：chunk 大小、重叠、元数据过滤（按业务域/文档类型过滤）、混合检索（向量 + 关键词 BM25）、rerank 重排。
- 评估：召回率/命中率，用"测试问题集"人工评估 TopK 质量。

**【项目案例】** 运费规则的切分策略：按"条款"为粒度（自然边界 > 固定 token），每条带 `{条款号, 生效日期, 适用线路}` 元数据；查询"北京到上海 5 吨的价格"先按线路元数据过滤，再向量召回 TopK——**元数据过滤把检索从"大海捞针"变成"定向捞针"**，命中率提升明显。

## 5-9. AI 辅助编程你怎么用？对前端开发的影响？（★★）

**详细回答（口述稿）：**
> "AI 辅助编程我是深度使用者，按用途分四类：一是代码生成——写模板代码、重复组件、样式布局，效率提升明显；二是解释和重构——读不懂的老代码让 AI 解释，重构前让它列风险点；三是测试和补全——生成单测用例、补边界条件；四是写文档和 commit——总结变更、生成文档。我的使用原则三条：一是 AI 输出必须 review——我理解每一行才合入，它是'加速器'不是'决策者'；二是让它做'有明确验收标准'的活——生成函数、表单组件，而不是让它设计架构；三是给上下文——把需求、接口定义、现有代码风格贴给它，输出质量差很多。对前端行业的影响我的判断：低水平的模板代码需求会减少，但'能定义问题、能把控质量、懂业务'的工程师价值反而上升——因为 AI 放大的是判断力。我补充一个实践：在项目里我们把接口文档喂给 AI 生成页面骨架，再人工 review，交付速度提升明显。"

**答案要点：**
- 使用场景：代码生成（组件/工具函数）、解释陌生代码、写单测、Code Review 辅助、文档生成、正则/算法片段。
- 效率收益：重复性代码（CRUD 页面、表单校验、配置）效率提升明显；复杂业务逻辑仍需人工把关。
- 风险与对策：代码质量参差（要 review）、安全漏洞（提示词注入、依赖）、过度信任（幻觉 API）；对策 = 小步提交 + 单测 + 安全扫描。
- 对岗位的影响：初级重复工作被替代，**"理解业务 + 架构设计 + 集成 AI"能力更值钱**；AI 是放大器不是替代者。

**【项目案例】** 项目实践：用 AI 辅助生成了 `docs/` 知识库的骨架（先扫描 1780 文件生成事实，再写文档）、接口清单脚本 `extract-api.js`（正则提取 1764 接口）、AI 聊天组件 demo。**真实贴士**：让 AI 干活前先把"事实输入"喂给它（文件清单、接口清单、规范），输出准确率翻倍——这是把 AI 编程工程化的关键认知。

## 5-10. 大模型前端未来会怎么发展？你如何保持竞争力？（★）

**详细回答（口述稿）：**
> "大模型跟前端的关系，我的判断是'从工具到架构'。近期是 AI 辅助开发——Copilot 类工具提升编码效率；中期是 AI 原生应用——对话式交互、自然语言操作、Agent 自主完成任务成为 UI 的一部分，前端要会做流式渲染、工具调用界面、多轮状态管理；远期是 UI 生成——根据描述生成界面，前端从'写代码'转向'定义交互和体验'。我的竞争力规划三条：一是把 AI 应用工程化能力做深——RAG、Agent、结构化输出、流式交互这套我已经在项目里落地，继续跟进；二是保持前端基本功的深度——框架原理、性能、架构，因为 AI 生成代码越容易，'判断代码好坏'的能力越值钱；三是业务理解力——AI 落地最大瓶颈是懂业务的人，我把物流业务和 AI 结合的经验沉淀下来。我总结：技术会迭代，但'定义问题 + 把控质量 + 理解业务'这三件事 AI 替代不了，我往这个方向积累。"

**答案要点：**
- 趋势判断：
  1. **AI 原生前端**：对话式交互成为标配（Copilot 面板、自然语言操作后台）。
  2. **组件智能生成**：低代码 + AI 生成页面，开发者转向"数据模型 + 规则"定义。
  3. **Agent 化业务系统**：AI 直接操作业务（查单、审批、调度），前端是"人机交互 + 可信执行"界面。
  4. **端侧模型**：小模型在浏览器/设备上跑（WebGPU/WASM），隐私与离线能力提升。
- 前端工程师的新技能：Prompt/Agent 编排、结构化输出、AI 工具链（Dify/LangChain）、评测体系（怎么验证 AI 功能好用）。
- 保持竞争力：深耕一个行业（物流）+ 掌握 AI 应用工程化 + 保持架构能力（多端、性能、安全）——**"业务深度 × AI 广度"**。

**【项目案例】** 收尾点题：我的 aiChat 组件已经把"流式对话 + 多会话 + 工具调用 + 白名单"做成可复用资产，下一步目标是把它做成平台的"AI 助手基础设施"，让订单、财务、客服各域页面都能一键接入。讲愿景时落到"下一步具体做什么"，比空谈趋势有说服力。
