## 1-1. 原型链与继承（★★）

**详细回答（口述稿）：**
> 先说说原型链，它是一个往上溯源查找对象属性的机制，里面主要有两个关键属性，prototype和__proto__，其中一个是函数独有的，一个是对象的，有个比较特殊的就是Function.prototype === Object.__proto__，因为Object被认为是Function的构造函数。然后说道继承，继承一开始主要是原型链继承和构造函数继承，但是父函数共享，后续衍生出了组合继承，就是在构造函数上面用原型链继承，但是会导致构造函数执行两次。后续又发展到寄生组合继承，例如Object.create复制一个新的原型链出来，后来es6的class...extend就是基于这个发展而来的，然后现代更多的偏向混入组合了。例如Object.assing和mixin，能混入组合基本不会做深层次的继承了。

**标准答案：**
> “关于原型链，我会从机制原理、核心概念辨析、以及现代工程实践三个维度来聊。
第一，机制上，它本质上是对象属性的查找机制，或者说是一个‘溯流’过程。
当访问一个对象的属性时，如果自身没有，JavaScript 引擎就会沿着内部指针 [[Prototype]] 向上游回溯查找，直到 Object.prototype，如果还找不到，就在 null 处停下。这种动态委托机制，是 JS 实现复用的底层基础。
第二，要真正掌握它，必须理清 prototype 和 __proto__ 的核心区别。如果用一句话总结：
prototype 属于函数，是构造函数独有的属性，指向一个原型对象，这个对象将作为其实例对象的公共祖先，挂载在上面的方法会被所有实例共享。
__proto__ 属于对象（包括函数对象），它是每个实例都有的内部属性（访问器），指向其构造函数的 prototype。它决定了当前对象在原型链上能‘看到’谁。
这里要注意，现在更推荐用 Object.getPrototypeOf() 来读取原型，而不是直接操作 __proto__。
第三，回到实际开发，继承方案的演进和取舍。
ES6 的 class extends 虽然底层用寄生组合继承解决了父类构造函数的重复调用问题，让‘归类’变得很清晰。但在现代前端工程（尤其是 React Hooks 和 Vue Composition API 盛行后），我们不再把 extends 当作唯一解，反而更偏向组合（Composition）。
因为继承树一旦过深，就会带来强耦合和难以调试的问题。现在遇到可复用逻辑，我会优先用Object.assign 做属性混入（Mixin），或者直接抽象出独立的函数模块进行逻辑组合。比如在封装表格组件时，我不会让所有业务表都继承同一个基类，而是把分页逻辑、筛选逻辑写成独立的组合式函数（Composables）或高阶组件，再用 Object.assign 混入到各个业务组件中。
所以，我的结论是：原型链是 JS 运行时的底层物理定律，我们必须懂；但工程架构上，组合（Mixins / Object.assign / Hooks）正在取代深层的继承树，让代码更灵活、更易于维护。 两者结合使用，才能写出既稳健又优雅的代码。”

**答案要点：**
- 每个对象都有 `__proto__` 指向其构造函数的 `prototype`，查找属性沿 `__proto__` 链向上，直到 `Object.prototype`，再上层为 `null`。
- `prototype` 是函数独有的属性；`__proto__` 是对象访问原型的标准方式（规范中为 `[[Prototype]]`）。
- 继承方式演进：原型链继承 → 构造函数继承（call/apply）→ 组合继承 → 寄生组合继承（最推荐）→ ES6 `class extends`（本质仍是寄生组合）。
- `new` 做了什么：①创建空对象 ②绑定原型 ③执行构造函数、绑定 this ④返回对象（函数显式返回对象则用该对象）。

**【项目案例】** 项目中的公共基础类 `BaseTable`（表格基类）通过 `class ... extends` 继承 Element UI 的 `Table` 组件，再被订单表、库存表等 40+ 业务表格复用；基类统一封装了分页、合计、列配置逻辑，子类只需覆盖 `head` 配置与数据加载方法。

```js
// 寄生组合继承核心
function inherit(Child, Parent) {
  Child.prototype = Object.create(Parent.prototype)
  Child.prototype.constructor = Child
}
```

## 1-2. 闭包与内存泄漏（★★★）

**详细回答（口述稿）：**
> "闭包一句话：函数 + 它声明时的词法作用域。内部函数引用了外部函数的变量，这个变量就不会被 GC 回收，从而形成闭包。它的价值是能造私有变量，模块模式、防抖节流、柯里化背后都是闭包。但闭包也是内存泄漏的重灾区——全局变量引用没释放、定时器和事件监听没清除、闭包里还攥着大对象、DOM 引用没置空。我的排查手段是 DevTools Memory 面板做堆快照对比，看对象是否只增不减。举项目里的例子：我们大屏看板每 5 秒 `setInterval` 轮询，如果不在 `beforeDestroy` 里 `clearInterval`，组件切走还在跑，内存只会往上走；地图轨迹回放组件销毁时还要移除 BMap 的事件和覆盖物，否则轨迹 Polyline 一路堆积。所以我现在写代码的习惯是——谁创建谁销毁，定时器、监听器成对清理。"

**答案要点：**
- 闭包 = 函数 + 其声明时的词法作用域。内部函数引用外部函数变量时形成闭包，变量不会被 GC 回收。
- 应用：私有变量、模块模式、防抖节流、柯里化、计数器。
- **内存泄漏场景**：全局变量引用未释放、定时器/事件监听未清除、闭包持有大对象、DOM 引用未置空。
- 排查：Chrome DevTools Memory 面板做堆快照对比，`performance.memory`、`--inspect` Node 分析。

**【项目案例】** 项目中有大量 `setInterval` 轮询（大屏看板每 5s 刷新、首页待办轮询），在 `beforeDestroy` 中统一 `clearInterval`；地图轨迹回放组件在销毁时移除 `BMap.Map` 事件与覆盖物，避免轨迹点 Polyline 堆积导致内存上涨。

## 1-3. this 指向与箭头函数（★★）

**详细回答（口述稿）：**
> "`this` 是在调用时确定的，按优先级排：new 绑定 > 显式绑定（call/apply/bind）> 隐式绑定（对象.方法）> 默认绑定（非严格模式是 window，严格模式是 undefined）。我的判断口诀是：普通函数谁调用指向谁，箭头函数定义在哪指向哪。箭头函数没有自己的 `this`，沿词法作用域向上找，所以它不能当构造函数、没有 `arguments`、`call/apply/bind` 也改不了它的指向。Vue2 项目里最常见的坑就是回调里 `this` 丢了——我们 `postUrl` 的 then 回调里用箭头函数，或者提前 `const self = this` 存一下；表格行事件绑定也用箭头函数保实例。现在写代码我默认回调全用箭头函数，需要动态 this 才用普通函数 + bind。"

**答案要点：**
- `this` 在调用时确定：默认绑定（严格模式 undefined）、隐式绑定（对象.方法）、显式绑定（call/apply/bind）、new 绑定（优先级最高）。
- 箭头函数没有自己的 `this`，沿词法作用域向上查找；也不能作为构造函数、没有 `arguments`、不能用 `call/apply/bind` 改变指向。
- 判断口诀：谁调用指向谁（普通函数）；定义在哪指向哪（箭头函数）。

**【项目案例】** 项目里 `common.postUrl(url, params).then(successFn)` 回调中，为保持组件实例，回调统一用箭头函数或提前 `const self = this`；表格行事件绑定用箭头函数避免 `this` 丢失，这是 Vue2 项目里最常见的 this 陷阱。

## 1-4. 手写 call / apply / bind（★★★）

**详细回答（口述稿）：**
> "手写的核心思路是'借方法'：call 就是把函数临时挂到目标对象上调用，这样函数里的 this 就自然指向那个对象。实现要点有三个：一是 `thisArg` 传 null/undefined 时在非严格模式下要指向全局对象；二是用 `Symbol` 生成唯一属性名，避免覆盖对象上已有的同名属性；三是调完记得 `delete` 清理。apply 只是参数从数组展开。bind 更特殊：它返回一个新函数并预置参数（支持柯里化），而且当返回的函数被 `new` 调用时，this 要指向新创建的实例而不是绑定的对象，所以要在内部用 `this instanceof bound` 判断一下。这个知识点我不光会背，项目里 `common.checkFn` 这类函数守卫和右键菜单的 `bind` 预置业务参数，用的就是这个机制。"

**答案要点：**
- call：`fn.call(thisArg, ...args)`，立即执行；apply 传数组。
- 实现思路：把 fn 挂到 `thisArg` 对象上调用，利用对象方法调用时 `this` 指向对象；注意 `thisArg` 为 null/undefined 时指向全局（非严格模式），并用 Symbol 避免属性冲突。
- bind：返回新函数，预置参数（柯里化），支持 `new` 调用（此时 this 指向新对象而非绑定的 thisArg）。

```js
Function.prototype.myBind = function (ctx, ...args) {
  const fn = this
  const bound = function (...rest) {
    return fn.apply(this instanceof bound ? this : ctx, [...args, ...rest])
  }
  bound.prototype = Object.create(fn.prototype)
  return bound
}
```

**【项目案例】** 项目工具函数库中封装了 `common.checkFn`（函数守卫）与 `myTab` 右键菜单绑定，处理回调时用 `bind` 预置业务参数，避免每层闭包重复传参。

## 1-5. Promise 原理与手写实现（★★★）

**详细回答（口述稿）：**
> "Promise 本质是状态机：pending 只能转到 fulfilled 或 rejected，且一旦落定不可逆。它解决的是回调地狱，核心机制是 `then` 返回新的 Promise，所以能链式调用、异常能向后透传。手写时三个关键点：一是回调要异步执行，先把 onFulfilled/onRejected 存进数组，等同步代码跑完再触发，所以 then 回调属于微任务；二是 `then` 的返回值如果是 Promise 要递归接上；三是 `all` 一个失败全失败、`race` 先到先得、`allSettled` 等全部落定。这个我在项目里其实每天都在用——我们 `common.postUrl` 就是用 `new Promise` 包住 XHR，成功 resolve、失败 reject；还维护了一个 `urlManager` Map 做防重复请求，同一接口 pending 期间直接返回同一个 Promise。可以说全项目 1764 个接口调用统一，靠的就是这一层 Promise 封装。"

**答案要点：**
- Promise 三种状态：pending → fulfilled / rejected，状态一旦改变不可逆。
- 解决回调地狱；`then` 返回新 Promise 支持链式；异常透传。
- 关键点：**异步执行回调**（存入数组，等同步代码执行完再 resolve/reject）；`then` 返回值可能是 Promise 需要递归处理；`all` 一个失败即失败、`race` 先到先得、`allSettled` 全部落定。
- 微任务：Promise 回调属于微任务，优先于宏任务（setTimeout）执行。

**【项目案例】** `common.postUrl` 就是基于 Promise 封装：内部用 `new Promise((resolve, reject) => ...)` 包住 `XMLHttpRequest`，请求成功后 `resolve(JSON.parse(xhr.responseText))`，失败 `reject`；并维护 `urlManager` Map 做防重复请求，同一接口 pending 期间直接返回已存在的 Promise。这就是"一个 RPC 封装如何让全项目 1764 个接口调用统一"的答案。

## 1-6. async/await 与事件循环（★★★）

**详细回答（口述稿）：**
> "async/await 是 Promise 的语法糖：async 函数必然返回 Promise；await 会暂停当前协程，等 Promise 落定后把后续代码注册为微任务继续执行，所以它不会阻塞主线程。错误处理用 try/catch，没捕获的 rejection 会触发 unhandledrejection。两个实战要点：一是在循环里用 await 会退化成串行，应该用 `Promise.all` 并行；二是 await 后面的代码一定在微任务队列里跑。我们项目里微信下单页就是先 `await` 地址分词拿省市区，再 `await` 拉字典数据初始化表单，两者有依赖所以串行；而地图轨迹的定位历史跟超速分析没有依赖，就用 `Promise.all` 一次等两组数据，省掉一倍的等待时间。"

**答案要点：**
- async 函数返回 Promise；await 暂停函数执行，等 Promise 落定后恢复，且不影响主线程（把后续代码注册为微任务/协程挂起）。
- 错误处理：try/catch 捕获；未捕获的 rejection 会导致 unhandledrejection。
- 与 Promise 对比：语义更清晰、顺序执行更直观，但要注意**串行陷阱**（循环内 await 变成串行，可用 Promise.all 并行）。
- await 后面的代码一定在微任务队列中执行。

**【项目案例】** 微信端下单页 `addOrder.js` 中，先 `await` 调用 `getSplitAddress`（地址分词）拿到省市区，再 `await` 调 `getSysStaticData` 拿字典数据初始化表单，两处 await 串行但彼此依赖；而地图轨迹 `monitorTF.locationHis` 与超速分析可并行时用 `Promise.all` 一次等待两组数据。

## 1-7. 微任务与宏任务执行顺序（★★）

**详细回答（口述稿）：**
> "一句话概括：每轮事件循环先取一个宏任务执行，然后清空所有微任务，再决定要不要渲染，最后才取下一个宏任务。宏任务有 setTimeout、setInterval、I/O、rAF；微任务有 Promise.then、queueMicrotask、MutationObserver。所以经典输出题 `console.log(1); setTimeout(()=>console.log(2)); Promise.resolve().then(()=>console.log(3))` 输出是 1、3、2。项目里有个细节：大屏每 5 秒 setTimeout 拉数据更新，更新完用 `$nextTick` 确认 DOM 已更新再滚列表，而 `$nextTick` 内部就是微任务——正因为微任务先于下一轮宏任务，数据刷新和动画滚动的节奏才不会打架。"

**答案要点：**
- 宏任务：`setTimeout`、`setInterval`、`setImmediate`、I/O、UI 渲染、`requestAnimationFrame`（渲染相关）。
- 微任务：`Promise.then`、`queueMicrotask`、`MutationObserver`、`process.nextTick`（Node）。
- 每轮事件循环：取一个宏任务 → 执行 → 清空所有微任务 → 渲染（如果需要）→ 取下一个宏任务。
- 经典输出题：`console.log('1'); setTimeout(()=>console.log('2')); Promise.resolve().then(()=>console.log('3'));` → 输出 1、3、2。

**【项目案例】** 大屏看板每 5 秒 `setTimeout` 拉数据更新后，通过 `$nextTick`（内部走微任务）确认 DOM 已更新再滚动列表；正因为微任务先于下一轮宏任务，数据刷新与动画滚动的节奏才不打架。

## 1-8. 浏览器 EventLoop 完整机制（★★★）

**详细回答（口述稿）：**
> "浏览器是多进程架构：浏览器进程、GPU 进程、网络进程、每个 tab 一个渲染进程，渲染进程里有主线程、合成线程、光栅线程等。JS 跑在主线程，主线程维护宏任务队列和微任务队列。一帧的典型顺序是：处理事件 → requestAnimationFrame 回调 → 样式/布局/绘制 → requestIdleCallback 空闲回调。这里最核心的认知是——超过 50ms 的长任务会阻塞渲染和交互，是卡顿的主因。我项目里大数据表格卡顿就是主线程被同步创建几千个单元格 DOM 的长任务堵死的，解法分两层：第一层分页 + 服务端筛选，第二层按需渲染加 `requestIdleCallback` 分批插入 DOM，把渲染让位给空闲时间。"

**答案要点：**
- 浏览器多进程：浏览器进程、GPU 进程、网络进程、渲染进程（每 tab）。渲染进程含主线程、合成线程、光栅线程等。
- 主线程上跑 JS 的宏任务队列 + 微任务队列；`requestAnimationFrame` 在渲染前回调；`requestIdleCallback` 在空闲时回调。
- 每帧任务：处理事件 → rAF → 样式/布局/绘制 → rIC。
- 长任务（>50ms）会阻塞渲染与交互，是卡顿主因。

**【项目案例】** 项目大数据表格渲染卡顿，排查发现是主线程被同步创建几千个单元格 DOM 的长任务阻塞。解决方案：①分页 + 服务端筛选（第一版）②表格行按需渲染 + `requestIdleCallback` 分批插入 DOM。面试时可回答"长任务拆解 + 渲染时机让位"两个层次。

## 1-9. 深拷贝与浅拷贝（★★★）

**详细回答（口述稿）：**
> "浅拷贝只拷贝第一层，`Object.assign`、展开运算符、`Array.slice` 都是；深层对象仍然共享引用。深拷贝有三个梯度：最快的是 `JSON.parse(JSON.stringify())`，但它丢函数、undefined、Symbol，Date 变字符串，循环引用直接报错；所以生产上要递归手写，关键是用 WeakMap 记录已拷贝的对象解决循环引用；现在浏览器原生 `structuredClone` 支持 Map/Set/Date/循环引用，是首选。项目里"复制订单"功能就是深拷贝订单草稿对象，再重置订单号、时间字段，如果只浅拷贝，改复制单会污染原单。我们的深拷贝工具统一放 `common.js`，内部用 `Object.prototype.toString` 区分 Date/RegExp/Array 做分支拷贝。"

**答案要点：**
- 浅拷贝：`Object.assign`、展开运算符、`Array.slice` —— 只拷贝第一层。
- 深拷贝：`JSON.parse(JSON.stringify(obj))`（缺点：丢函数/undefined/Symbol/循环引用/Date 变字符串）→ 递归手写（处理循环引用用 WeakMap）→ `structuredClone`（现代浏览器原生，支持 Map/Set/Date/循环引用）。
- 注意：拷贝后对象间是否独立、特殊类型是否保留。

```js
function deepClone(obj, map = new WeakMap()) {
  if (obj === null || typeof obj !== 'object') return obj
  if (map.has(obj)) return map.get(obj)
  const clone = Array.isArray(obj) ? [] : {}
  map.set(obj, clone)
  for (const key in obj) {
    if (Object.prototype.hasOwnProperty.call(obj, key)) clone[key] = deepClone(obj[key], map)
  }
  return clone
}
```

**【项目案例】** 下单页在"复制订单"功能里用深拷贝复制订单草稿对象，再重置订单号/时间字段，避免改复制单时污染原单（浅拷贝会共享引用）；深拷贝工具在 `common.js` 中统一提供。

## 1-10. 数组去重与常用数组方法（★★）

## 1-11. 防抖与节流（★★★）

**详细回答（口述稿）：**
> "防抖和节流的区别一句话讲清：防抖是'事件停止后 delay 毫秒才执行，期间再触发就重置计时'，适合输入搜索、resize 结束、提交按钮防连点；节流是'固定间隔内最多执行一次'，适合滚动监听、鼠标移动、控制刷新频率。手写防抖就是 `setTimeout + clearTimeout`，注意透传 this 和参数；节流可以用时间戳版（立即执行）或定时器版（结束后执行）。项目里车辆监控的轨迹时间轴拖动、货主端搜索框都接了 300ms 防抖减少请求；大屏虽然用 setInterval 轮询，但把数据刷新函数节流了，防止上一次请求没返回就重复触发。这个题我一般会现场手写，因为考的是对'时机控制'的理解。"

**答案要点：**
- 防抖（debounce）：事件停止触发后 delay 毫秒才执行，期间重新触发则重置计时。适合输入搜索、resize 结束、提交按钮防连点。
- 节流（throttle）：固定时间间隔内最多执行一次。适合滚动监听、鼠标移动、大屏刷新频率控制。
- 手写要点：debounce 用 `setTimeout + clearTimeout`；throttle 用时间戳或定时器两种实现；都要注意 `this` 与参数透传。

```js
function debounce(fn, delay = 300) {
  let timer = null
  return function (...args) {
    clearTimeout(timer)
    timer = setTimeout(() => fn.apply(this, args), delay)
  }
}
function throttle(fn, interval = 500) {
  let last = 0
  return function (...args) {
    const now = Date.now()
    if (now - last >= interval) { last = now; fn.apply(this, args) }
  }
}
```

**【项目案例】** 车辆监控页的轨迹时间轴拖动、货主端搜索框输入，都接了防抖（300ms）减少请求；大屏看板虽用 `setInterval` 轮询，但把数据刷新函数节流，防止上一次请求未返回时重复触发。

## 1-13. == 与 === 及隐式转换（★★）

**详细回答（口述稿）：**
> "=== 不做类型转换，== 会隐式转换，转换规则大致是：对象先转原始值（valueOf/toString），字符串转数字，布尔转数字。几个经典陷阱：`null == undefined` 为 true，`[] == false` 为 true（因为 [] 先变 '' 再变 0），`[1] == 1` 也为 true。所以规范建议一律用 ===，唯一例外是判断空值可以用 `val == null` 同时覆盖 null 和 undefined。项目里 `common.isEmpty` 为了语义清晰用了显式三条件 `undefined/null/''`；后端返回的金额字段可能是字符串，我们统一 `Number(x)` 转换后再比较，避免 `"100" == 100` 这类隐式坑。我的观点是：知道隐式规则是为了踩坑时能立刻定位，写代码时永远显式。"

- `+` 运算符注意：数字 + 字符串 = 字符串拼接。

**【项目案例】** 项目工具 `common.isEmpty` 里判断空值用 `val === undefined || val === null || val === ''`，显式三条件；接口返回的金额字段因后端可能返回字符串，统一用 `Number(x)` 转换后再做比较运算，避免 `"100" == 100` 的隐式陷阱。

## 1-16. 浏览器渲染机制与重排重绘（★★★）

**详细回答（口述稿）：**

## 1-17. HTTP 缓存机制（★★★）

**详细回答（口述稿）：**
> "HTTP 缓存分两层：强缓存和协商缓存。强缓存由 `Cache-Control`（max-age/no-cache/no-store 等）控制，命中就直接用本地缓存，不发请求，浏览器显示 200 from disk/memory cache；协商缓存是缓存过期后带 `Last-Modified/If-Modified-Since` 或 `ETag/If-None-Match` 问服务器，命中返回 304 不重新下载，ETag 是内容指纹优先级更高。完整流程：先看强缓存，过期再走协商缓存，都未命中才重新下载。项目里 `vue.config.js` 的部署策略是：js/css 带 contenthash 设一年强缓存，HTML 设 no-cache，实现'改代码必更新、不改代码用缓存'；登录态接口用 no-store 防止被缓存。我还会补一句：缓存配置本质是工程决策，要跟发布策略配套设计。"

**答案要点：**
- 强缓存：`Cache-Control`（max-age / s-maxage / no-cache / no-store / public / private）、`Expires`（HTTP1.0）。命中后 200 from disk/memory cache，不发请求。
- 协商缓存：`Last-Modified / If-Modified-Since`（秒级）、`ETag / If-None-Match`（内容指纹，优先）。命中返回 304。
- 流程：先看强缓存 → 过期后带条件头走协商缓存 → 都未命中才重新下载。
- 适用：静态资源（js/css/img）用强缓存 + 文件名 hash；HTML 用 no-cache。

**【项目案例】** `vue.config.js` 对打包产物配置：js/css 带 contenthash 并设一年强缓存，`public/index.html` 设 `no-cache`，实现"改代码必更新、不改代码用缓存"的部署策略；登录态用 `no-store` 防止被缓存。

## 1-21. Web 安全：XSS 与 CSRF（★★）

**详细回答（口述稿）：**
> "我把 Web 安全按'攻击从哪来'讲：XSS 是'脚本进来'，分存储型、反射型、DOM 型三种，防御靠转义输出、CSP 白名单、Cookie 加 HttpOnly，Vue 插值默认转义但 `v-html` 要特别小心；CSRF 是'请求伪造'，诱导已登录用户在不知情下发请求，防御靠 SameSite Cookie、请求头带自定义 token、Referer/Origin 校验、敏感操作二次确认。项目里我们封装了 `common.escapeHTML`，富文本和备注渲染时转义 `< > &`；登录 token 存内存，每次请求头部带自定义 header 供服务端校验，天然防 CSRF；iframe 嵌入页面用 X-Frame-Options 白名单防点击劫持。我还会强调安全意识：前端防的是体验层，真正的防线要前后端配合。"

**答案要点：**
- XSS（跨站脚本）：恶意脚本注入执行。分存储型（存库后展示触发）、反射型（URL 参数）、DOM 型。防御：转义输出、`CSP`（Content-Security-Policy）、HttpOnly Cookie、前端库默认转义（Vue 插值即转义，但 `v-html` 要小心）。
- CSRF（跨站请求伪造）：诱导用户在已登录站点发请求。防御：SameSite Cookie、token 校验（请求头带自定义 token）、Referer/Origin 校验、二次确认。
- 其他：点击劫持（X-Frame-Options）、SQL 注入、越权。

**【项目案例】** 项目统一封装 `common.escapeHTML`，在富文本/备注渲染时转义 `< > &` 等字符；登录接口返回的 token 存内存 + 每次请求头部携带自定义 header，服务端校验（防 CSRF）；iframe 嵌入外部页面加 `X-Frame-Options` 白名单控制。

## 1-22. 前端性能优化全景（★★）

**详细回答（口述稿）：**
> "性能优化我会按三个阶段讲，避免只说散点：加载阶段——资源 gzip/CDN、图片压缩 WebP、路由懒加载、组件按需引入、preload/prefetch；渲染阶段——减少重排重绘、骨架屏、虚拟滚动、web worker 分担计算；运行时——防抖节流、事件委托、代码分割、长任务拆分。衡量指标上，加载看 FP/FCP/LCP，稳定看 CLS，交互看 INP/TTI，配合 Lighthouse 和 webpack-bundle-analyzer 定位。项目首屏优化三板斧：路由全量懒加载、Element UI 按需引入、大屏独立 chunk；pt 端 1585 个接口调用分散到 40+ 页面 chunk，做到'用哪个页面加载哪个页面'。答这题的关键是'有指标、有工具、有案例'三层都有。"

**答案要点：**
- 加载阶段：资源压缩（gzip/brotli）、CDN、HTTP2、雪碧图/字体图标、图片压缩与 WebP、路由懒加载、按需引入组件库、preload/prefetch、减少重定向。
- 渲染阶段：减少重排重绘、`content-visibility`、骨架屏、SSR/预渲染、虚拟滚动、web worker 分担计算。
- 运行时：防抖节流、事件委托、缓存计算、代码分割、长任务拆分。
- 衡量指标：FP/FCP/LCP（加载）、CLS（布局偏移）、INP/TTI（交互）、FPS。
- 工具：Lighthouse、Performance、webpack-bundle-analyzer。

**【项目案例】** 项目首屏优化三板斧：①路由全量懒加载（myTab 动态 import 页面 chunk）②Element UI 按需引入（babel-plugin-component）③大屏页面独立 chunk；登录后按端只加载对应模块的菜单与组件，pt 端 1585 个接口调用分散到 40+ 页面 chunk，实现"用哪个页面加载哪个页面"。

## 1-23. TCP 三次握手与四次挥手（★）

**详细回答（口述稿）：**
> "三次握手是为了确认双方收发能力都正常：客户端发 SYN，服务端回 SYN+ACK，客户端再回 ACK，就建立了连接。四次挥手因为 TCP 是半关闭的，两端的关闭要分开处理：A 发 FIN，B 回 ACK，B 再发 FIN，A 回 ACK，中间会经历 TIME_WAIT 2MSL 让旧包消失。跟 HTTP 的关系：HTTP/1.1 的 keep-alive 复用连接就是为了省去频繁握手。项目里我们用了 HTTPS + keep-alive，同一域名连接复用，避免每个请求都重新三次握手；这个点我一般会顺势引出 HTTP/2 多路复用怎么解决队头阻塞，展示知识是成体系的。"

**答案要点：**
- 三次握手：SYN（客户端）→ SYN+ACK（服务端）→ ACK（客户端）。确保双方收发能力正常。
- 四次挥手：FIN → ACK → FIN → ACK。因为 TCP 半关闭特性，两次 FIN 分离。
- 状态：TIME_WAIT 2MSL 等旧包消失。
- 与 HTTP 的关系：HTTP/1.1 keep-alive 复用连接减少握手。

**【项目案例】** 项目使用 HTTPS + HTTP/1.1 keep-alive，同一域名连接复用，避免每请求都三次握手；这也是 HTTP/2 多路复用进一步解决"队头阻塞"的引出点。

## 1-24. WebSocket 与实时通信（★）

**详细回答（口述稿）：**
> "WebSocket 是一次 HTTP Upgrade 握手后建立的全双工持久连接，服务端可以主动推送，适合聊天、看板、地图定位这类场景，要注意断线重连、心跳、wss 加密这些工程细节。这个题我更想讲的是'选型权衡'：我们大屏看板和车辆监控用的是短轮询——每 5 秒 setInterval 拉一次数据，而不是 WebSocket。原因是 SaaS 多租户场景接口统一走 HTTP 网关，轮询成本低、兼容性好、不用维护长连接和心跳；如果业务要求秒级实时，再升级 WebSocket。答这个题主动讲'为什么选轮询'，比单纯背 WebSocket 特性更能体现架构权衡能力。"

**答案要点：**
- WebSocket 全双工、一次握手（HTTP Upgrade）后持久连接，服务端可主动推送。
- 与轮询/长轮询（SSE 单工）对比：实时性高、开销小。
- 应用：聊天、看板、地图定位推送、协同编辑。
- 注意：断线重连、心跳机制、跨域、wss 加密。

**【项目案例】** 大屏看板与车辆监控采用"短轮询 + 定时器"实现准实时（每 5s `setInterval` 拉一次），而非 WebSocket——原因是 SaaS 多租户场景接口统一走 HTTP 网关，轮询成本低、兼容性好；若要求秒级实时推送，再升级为 WebSocket 长连接。面试主动讲"为什么选轮询"体现架构权衡能力。

## 1-25. 经典代码输出题汇总（★★）

**详细回答（口述稿）：**
> "代码输出题我建议'边写边解释'，展示的不只是答案而是思路。这几道都是高频：变量提升题输出 undefined，因为 var 只提升声明；闭包陷阱题 `for (var i...)` 里 setTimeout 全输出 3，因为 var 共享同一个 i，改成 let 就是 0、1、2；事件循环题按'宏任务先进队列、微任务先清空'推，输出 a、d、c、b；箭头函数的 this 沿定义作用域找，所以 obj.fn() 输出 window；`[] == ![]` 隐式转换两边都变 0 所以是 true；`[1,2,3].map(parseInt)` 因为 parseInt 接收了 index 当进制参数，输出 [1, NaN, NaN]。最后这题我在项目里真实踩过：Vue 列表用 var 绑定行点击事件，取到的永远是最后一行的索引，改 let 修复——这就是面试官最爱问的闭包陷阱实战版。"

**答案要点：**
```js
// 1) 变量提升
console.log(a); var a = 1;          // undefined
// 2) 闭包陷阱
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0)  // 3 3 3（var 共享）; 改 let 或闭包得 0 1 2
}
// 3) 事件循环
console.log('a');
setTimeout(() => console.log('b'), 0);
Promise.resolve().then(() => console.log('c'));
console.log('d');                     // a d c b
// 4) this
const obj = { fn: () => { console.log(this) } }
obj.fn()                             // window（箭头函数无 this，沿定义作用域）
// 5) 隐式转换
console.log([] == ![]);              // true
// 6) 数组方法返回值
[1,2,3].map(parseInt)                // [1, NaN, NaN]（parseInt 接收 index 参数）
```

**【项目案例】** 项目中真实踩过的坑：`for (var i...)` 内绑定行点击事件，取到的一律是最后一行的 i，后用 `let` + 闭包修复——这是 Vue2 列表里"事件拿到错误索引"的最常见原因，也是面试官最爱问的闭包陷阱实战版。
