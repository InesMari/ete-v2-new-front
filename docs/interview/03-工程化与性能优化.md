## 3-1. Webpack 构建流程（★★★）

**详细回答（口述稿）：**
> "Webpack 的构建流程我概括成四步：初始化——读配置、加载 plugin；编译——从 entry 出发，loader 把模块转成 JS，递归解析依赖图；生成——依赖图处理完，按 optimization 规则把模块分包成 chunk，hash 命名；输出——写入 dist。核心概念串起来说：entry 是起点，loader 让 Webpack 能处理非 JS 文件（转译、压缩、编译 CSS/图片），plugin 贯穿整个生命周期做钩子增强（HtmlWebpackPlugin 注入 HTML、SplitChunksPlugin 分包、MiniCssExtractPlugin 抽 CSS），output 定产物。项目里 vue.config.js 就是围绕这套流程配置的：多入口区分 pt/hz/wx 端、SplitChunks 把公共组件库和业务拆开、生产开 gzip。答完我会强调：loader 管'文件到模块'，plugin 管'流程到产物'，这是两个容易混的概念。"

**答案要点：**
- 核心概念：entry（入口）、output（出口）、module（模块）、chunk（代码块）、loader（转换）、plugin（插件）、resolve（解析）。
- 构建流程：①初始化参数 + 配置合并 ②从 entry 出发，递归解析依赖（loader 转换 → AST → 依赖收集）生成模块图 ③按 chunk 打包 ④plugin 在生命周期钩子中介入（Tapable 事件流）⑤输出文件到 output。
- loader 是"文件转换器"（右→左执行，pitch 可左→右）；plugin 是"打包器增强"（整个构建生命周期挂钩子）。
- 常用配置：`output` 带 hash、`optimization.splitChunks` 拆包、`devServer` 热更新。

**【项目案例】** `vue.config.js` 的核心配置：`chainWebpack` 给公共库（vue/element-ui/vant）打 `vendor` 缓存组、页面动态 import 自动拆 chunk（`webpackChunkName`）、`babel-plugin-component` 实现 Element UI 按需引入；`filename` 带 contenthash 配合 `index.html` no-cache 实现"改代码必更新"的缓存策略。

## 3-2. Webpack loader 与 plugin 的区别与开发（★★）

**详细回答（口述稿）：**
> "loader 和 plugin 的分工一句话：loader 是'转换器'，把一种文件转成 Webpack 能处理的模块，职责单一、链式执行、靠 export 函数；plugin 是'扩展器'，监听 webpack 生命周期钩子在特定时机干特定事，本质是 class + apply(compiler)。开发上 loader 关注输入输出、保持纯函数；plugin 要熟悉 compilation/compiler 的钩子。项目里我写过自定义 loader 处理小程序端的 wxss 适配、用 plugin 在构建后注入环境变量和版本号。答这个题我会强调：不是每个项目都要自己写 loader/plugin，但理解了它们的边界，看 vue.config.js 和 webpack 报错时就不会慌。"

**答案要点：**
- loader：处理单个文件，把 A 语言/格式转成 B（如 sass→css→js 模块）；函数式，`this` 是 loader context，可 `this.callback` 或返回 `[result, map]`。
- plugin：监听 webpack 生命周期事件（compiler/compilation），可做资源处理、产物修改、环境注入（DefinePlugin）、打包分析（BundleAnalyzerPlugin）。
- 开发 loader：`module.exports = function(source) { return source.replace(...) }`；开发 plugin：class + `apply(compiler)` + `compiler.hooks.emit.tap(...)`。
- 常用：`MiniCssExtractPlugin`、`HtmlWebpackPlugin`、`TerserPlugin`、`CopyPlugin`。

**【项目案例】** 项目把 SVG 图标用 `svg-sprite-loader`（loader）合并成雪碧图，页面按需引用 symbol；自定义了一个 plugin 在打包后把产物清单输出到 `build.json`，供 CI 脚本读取版本号发版——从"用 loader"到"写 plugin"是工程化深度的分水岭。

## 3-3. Vite 与 Webpack 对比（★★★）

**详细回答（口述稿）：**
> "Vite 和 Webpack 的本质区别在开发模式：Webpack 先打包再启动，项目大时冷启动和热更新都慢；Vite 基于 ESModule，启动时不用打包，浏览器直接请求模块文件，秒开，依赖用 esbuild 预构建、按需加载，所以 HMR 快到毫秒级。生产上 Vite 用 Rollup 打包，产物同样能做 tree-shaking 和分包。选型考虑：新项目、追求开发体验、纯前端应用选 Vite；老项目、深度依赖 webpack 生态插件、需要高度自定义的继续 Webpack。项目是 Vue2.6 + Vue CLI 4 的老架构，我没有贸然迁移——迁移成本不只是改配置，还牵扯 loader、插件、构建产物验证，收益主要在开发体验；新模块我会用 Vite 起。我的观点：工具选型要算'迁移 ROI'。"

**答案要点：**
- 开发体验：Vite 用**原生 ESM + esbuild 预构建**，按需编译、秒级冷启动、HMR 快；Webpack 全量打包、慢。
- 生产构建：Vite 用 Rollup（产物更小更干净）；Webpack 生态成熟、可配置度极高。
- 兼容性：Vite 要求浏览器原生 ESM（Vite 4/5 后普遍无虞）；Webpack 兼容 ES5 环境。
- 取舍：新项目、中小型、追求 DX → Vite；老项目、复杂自定义构建、强生态 → Webpack。
- 构建原理：Vite 依赖预构建（esbuild 把 CMD/UMD 转 ESM 并合并依赖）解决"请求瀑布"。

**【项目案例】** 老平台锁定 Vue CLI 4（Webpack 4）未贸然迁移（1780 文件、40+ 插件、复杂代理配置迁移成本高）；新 Vue3 系统从零搭建时直接选 Vite，AI 聊天模块开发热更新秒级反馈。面试讲"**老项目不折腾、新项目用新工具**"的迁移策略最加分。

## 3-4. 代码分割与懒加载（★★★）

**详细回答（口述稿）：**
> "代码分割的目的就一个：让用户只下载当前要用的代码。三种方式：入口点分割（多入口）、动态 import 分割（路由懒加载）、SplitChunksPlugin 分割（把公共依赖和业务拆开、把大第三方库单独 chunk）。懒加载是分割的消费端——用到才请求。项目里 40+ 页面全部 `() => import()` 路由懒加载，Element UI 按需引入，公共组件 vendor 单独 chunk 走缓存，大屏独立 chunk；导出库 excelOut、打印库 Lodop 都是组件级懒加载，不进首屏主包。效果是主包从 4.2MB 降到 1.1MB。我会补一句：分割粒度不是越细越好，chunk 太碎 HTTP 请求反而多，要平衡——我们控制在 40+ 个合理 chunk。"

**答案要点：**
- 三种手段：多入口、动态 import（路由懒加载/组件懒加载）、`optimization.splitChunks`（公共代码抽离）。
- 动态 import 返回 Promise，webpack 自动分包；`/* webpackChunkName: "xxx" */` 命名 chunk。
- splitChunks：`cacheGroups` 配置 vendor（node_modules 公共依赖）与 common（业务公共模块）。
- 加载策略：preload（当前页立即用）vs prefetch（空闲时预加载下一个可能页面）。

**【项目案例】** 项目打包产物策略：`vendor` 缓存组把 vue/element-ui/vant 打成一个长缓存 chunk；40+ 业务页按路由拆独立 chunk；`excelOut`、`lodop`（打印插件）等重型库动态 import。主包 4.2MB → 1.1MB（gzip 后约 350KB），首屏加载从 6s+ 降到 2s 左右。

## 3-5. Tree Shaking（★★）

**详细回答（口述稿）：**
> "Tree Shaking 就是'摇掉没用到的代码'：基于 ESModule 的静态 import/export 分析，构建时删除未被引用的导出。前提必须是 ESModule——CommonJS 的 require 是动态的，摇不了。另外代码要写在"副作用"之外，否则 `/*#__PURE__*/` 标记也救不了被当副作用保留的模块。项目里 vant 和 element 都按需引入（babel-plugin-import），效果就是只打包用到的组件；我自己封装 common.js 时也刻意保持纯函数、无副作用导出，配合 lodash-es 这类按需库，首屏体积直接受益。答这题我会提醒：Tree Shaking 不是加了就生效，组件库按需引入 + 自己的代码写纯净，两头都要做。"

**答案要点：**
- 依赖 ES Module 静态分析（import/export 不可动态），webpack 构建时摇掉未引用的导出。
- 条件：`mode: production`（自动开启）、模块是 ESM 写法（CommonJS require 无法摇）、副作用标记 `"sideEffects": false`。
- 注意：引入样式或带副作用的库要加 `sideEffects: ["*.css"]` 白名单，否则被误摇。
- 案例：`import { Button } from 'element-ui'` 全量引入无法摇 → 按需引入（babel-plugin-component）。

**【项目案例】** 项目通过 `babel-plugin-component` 把 Element UI 改为按需引入，配合 Vant 的按需导入，样式从"全量 CSS"变成"用到的组件样式"，CSS 体积减半；`utils/common.js` 这类纯函数工具模块标记 `sideEffects: false`，确保 Tree Shaking 生效。

## 3-6. 前端模块化演进（★★）

**详细回答（口述稿）：**
> "模块化演进我按时间线讲：最早的全局变量污染全局；IIFE 靠闭包造局部作用域（模块模式）；CommonJS 服务端用、require 同步；AMD/CMD 浏览器端异步加载；ESModule 是标准方案，静态分析、编译期确定、支持 tree-shaking。演进的核心诉求就三个：隔离作用域、管理依赖、按需加载。项目里打包产物能看出这代际——Webpack 最终把 ESModule 编译成运行时模块包装（webpack 模块运行时），浏览器不认识 import 就用不了原生 ESM。这也是为什么 Vite 能秒开：它直接利用浏览器原生 ESM。答这个题建议画个时间轴，展示你理解'每个方案解决什么问题、带来什么新问题'。"

**答案要点：**
- IIFE（全局污染）→ CommonJS（同步 require，服务端）→ AMD/CMD（异步，浏览器端）→ ES Module（标准，静态分析，tree-shaking 基础）。
- ESM 特点：`import` 提升、只读引用、支持顶层 await；浏览器原生支持后无需打包器即可跑现代应用。
- UMD = 兼容 CommonJS + AMD + 全局。
- 工程意义：模块化是组件化、单元测试、按需加载的地基。

**【项目案例】** 项目三文件分离模式（`.vue` 模板 + 同名 `.js` 逻辑 + 可选 `.scss`）本质是"组件即模块"；工具库 `common.js` 用 ESM 具名导出 65+ 方法，业务页 `import { postUrl, formatDate } from '@/utils/common'` 按需引用，配合 Tree Shaking 保证工具库再大也不影响主包体积。

## 3-7. Babel 工作原理（★★）

**详细回答（口述稿）：**
> "Babel 的流程是一条三阶段流水线：解析（parse）——把源码转成 AST；转换（transform）——插件对 AST 做修改，这是核心，preset-env 就是一组按目标环境组合的转换插件；生成（generate）——把 AST 再转回代码。配置上 `.babelrc` 用 `@babel/preset-env` 按 browserslist 目标自动决定转哪些语法，`useBuiltIns` 按需引入 polyfill。项目 babel.config.js 里除了 preset-env 还配了 `babel-plugin-import` 实现 Element UI 按需引入——本质就是 AST 转换插件，把 `import { Button }` 改写成 `import Button from 'element-ui/lib/button'`。答这题展示'会配 + 理解 AST 转换'两个层次，高级感就有了。"

**答案要点：**
- 三步骤：解析（parse，源码 → AST）→ 转换（transform，插件修改 AST）→ 生成（generate，AST → 目标代码）。
- 核心包：`@babel/parser`、`@babel/traverse`、`@babel/generator`、`@babel/core`。
- preset（预设）= 插件集合：`preset-env`（按 browserslist 转语法）、`preset-react`、`preset-typescript`。
- plugin-transform-runtime 注入 helper 与 polyfill（减少重复代码、避免污染全局）。
- `core-js` 提供新 API polyfill（Promise、includes 等）。

**【项目案例】** `babel.config.js` 配置：`presets: [['@vue/cli-plugin-babel/preset', { useBuiltIns: 'usage' }]]`——按目标浏览器按需注入 polyfill，老客户环境（IE11 兼容的旧车载终端）也能跑；`@babel/plugin-transform-runtime` 抽离 helper，多 chunk 间复用公共代码。

## 3-8. 构建体积与速度优化（★★）

**详细回答（口述稿）：**
> "构建优化分两个目标说。体积：路由懒加载、按需引入组件库、压缩（terser 去注释、gzip/brotli）、CDN 外链公共库、移除多余依赖、Tree Shaking。速度：`cache-loader`/持久化缓存、`thread-loader`/`happypack` 多线程、`DllPlugin` 预编译不常变的库、缩小 loader 的 include 范围、换 esbuild 转译。项目里我做过三件事：把 lodash 全量引入改成按需，体积降了 300KB；Element UI 按需引入主包降 40%；加 babel 缓存和多线程编译，本地构建从 90 秒压到 40 秒。我会强调：优化前先用 webpack-bundle-analyzer 看体积分布，别凭感觉优化——数据驱动。"

**答案要点：**
- 体积：按需引入、Tree Shaking、代码分割、图片压缩（imagemin）、gzip（compression-webpack-plugin）、移除 console（terser drop_console）。
- 速度：`thread-loader`/`parallel-webpack` 多进程、`cache-loader`/`babel-loader cacheDirectory` 缓存、`DllPlugin` 预编译公共库（webpack4 后 splitChunks 可替代）、`speed-measure-webpack-plugin` 定位耗时、减少无谓 loader（exclude node_modules）。
- 产物分析：`webpack-bundle-analyzer` 看体积分布。

**【项目案例】** 项目 CI 脚本 `ci.sh` 流程：`npm run build` → 产物 gzip 到 `dist` → 上传 CDN → 读取 `build.json` 版本号通知部署；构建阶段用 `terser` 生产去 console 与注释、图片转 base64 阈值调低（>8KB 才内联）、公共依赖 `cacheGroups` 拆 vendor，最终产物 gzip 后 <2MB。

## 3-9. 前端监控与错误上报（★★★）

**详细回答（口述稿）：**
> "前端监控分三层：错误监控（JS 异常用 `window.onerror`、Promise 异常用 `unhandledrejection`、框架生命周期错误用 errorHandler 捕获）、性能监控（Performance API 拿 FP/FCP/LCP 等指标上报）、行为监控（用户点击、路由、关键接口耗时）。上报方式：构造 `new Image()` 的 src 打点或 `sendBeacon`（页面卸载也能发）。项目里我给大屏和订单系统做过轻量监控：`common.js` 里统一错误捕获，JS 异常和接口失败会聚合并带上用户、路由、堆栈上报；接口层还统计了每个请求的耗时和失败率，方便定位慢接口。我会强调：监控的目的不是'收集错误'而是'快速定位问题'，所以上报要带上下文（用户、页面、参数摘要、时间）。"

**答案要点：**
- 错误捕获：`window.onerror`（运行时错误）、`window.addEventListener('unhandledrejection')`（Promise 错误）、`window.onerror` 在跨域脚本要 `crossorigin` 属性。
- Vue 层：`Vue.config.errorHandler` 捕获组件渲染/生命周期错误。
- 上报：`navigator.sendBeacon`（页面卸载也能发）、`Image` 打点（GET 1x1）、`fetch` 带鉴权；批量上报防刷接口。
- 性能监控：`performance.timing`/`PerformanceObserver` 采集 LCP/CLS/INP，`web-vitals` 库。
- 质量闭环：错误堆栈 + sourcemap 还原（`source-map` 只上传不公开）。

**【项目案例】** 项目在 `common.js` 里统一挂了 `window.onerror` 与 `unhandledrejection`，捕获后 `sendBeacon` 上报 `sysLogService.saveSysLog`；`Vue.config.errorHandler` 捕获组件错误并自动带上路由与用户 id；sourcemap 上传到内网服务，生产环境不暴露。这套"错误闭环"能让 2000 用户的平台 80% 的报错在上线第一周被修复。

## 3-10. CI/CD 与前端交付（★）

**详细回答（口述稿）：**
> "CI/CD 我讲完整链路：CI 阶段——代码 push 触发流水线，先跑 lint + 单测 + 构建，任何一个失败就拦截；CD 阶段——通过后构建产物上传服务器/CDN，按环境分测试、预发、生产，关键节点人工确认；最后一步通知和回滚机制。工程上的配套：构建产物带 hash 支持版本回退、配置集中管理（环境变量区分接口地址）、发布脚本幂等。项目里用脚本化的发布流程（ci.sh）加 Nginx 多环境配置，构建产物按 hash 管理，测试环境随时可回滚到上一个版本。答这题我会强调：前端工程化的最后一步是'交付'，谁都不能只把代码写完就算完，CI/CD 让交付可重复、可回滚、可审计。"

**答案要点：**
- 流程：提交 → 触发流水线（lint + test + build）→ 产物上传 → 发布灰度/全量 → 监控告警。
- 常用：Jenkins/GitLab CI/GitHub Actions；Docker 镜像化部署；CDN 静态托管。
- 质量门禁：ESLint 不过不构建、单测覆盖率阈值、依赖安全检查（npm audit）。
- 前端特有：构建产物不可变（带 hash）、回滚 = 切回上一版本 CDN、多环境（dev/test/prod）配置注入。

**【项目案例】** 项目 `ci.sh`：`npm ci → lint → build → zip → scp 上传 CDN 目录 → 版本号写入接口`；多端（pt/hz/edu/wx）通过同一套源码不同入口配置构建出 5 个 SPA；发布脚本支持"灰度比例"参数，先放 10% 流量观察错误率再全量。这是从"手动拖文件"到"一键发布"的工程化升级，面试可量化到"发版时间从 30 分钟缩短到 3 分钟"。

## 3-11. 代码规范与 ESLint/Prettier（★★）

**详细回答（口述稿）：**
> "ESLint 和 Prettier 的分工：ESLint 管'代码质量'——语法错误、未用变量、危险写法；Prettier 管'代码风格'——缩进、引号、分号、换行。两者配合使用，规则冲突靠 `eslint-config-prettier` 关掉 ESLint 的格式类规则。工程落地三件套：husky + lint-staged 在 commit 前只检查改动的文件、ESLint 支持 `--fix` 自动修复、pre-commit 校验不通过直接拦截提交。项目里我们靠这套把 1780 个文件团队的代码风格统一住了：no-var 强制、箭头函数优先、组件命名 PascalCase、文件三件套（.vue/.js/.scss）规范。我会强调：规范最重要的不是规则本身，而是'用工具强制'——靠自觉的规范等于没有规范。"

**答案要点：**
- ESLint：静态检查，规则（no-var、eqeqeq、no-console）+ 自定义规则；配合 `eslint-plugin-vue` 检查模板。
- Prettier：代码格式化，统一风格（引号/分号/缩进）；与 ESLint 分工：Prettier 管格式，ESLint 管质量。
- Husky + lint-staged：commit 前只检查暂存文件，`lint-fix` 自动修复。
- 规范化收益：Code Review 聚焦逻辑而非格式；新人上手成本降低。

**【项目案例】** 项目配置 `eslint:recommended + plugin:vue/essential` + Prettier；`package.json` 里 `lint-staged` 对 `*.{js,vue}` 先 prettier 再 eslint --fix；Git hooks 拦截不合规提交。同时建了 `docs/web-01-开发规范.md` 沉淀 postUrl 命名、组件三文件分离、`v-entity` 权限使用等**团队约定**——规范文档与工具双管齐下。

## 3-12. 设计模式在前端的应用（★★）

**详细回答（口述稿）：**
> "设计模式我按'项目里真实用到'来讲，不背目录。观察者/发布订阅——Vue 响应式就是观察者模式，事件总线是发布订阅；单例——Vuex 的 store、请求的 urlManager 防重复队列；工厂——组件库的组件注册、动态生成表单字段；策略——表格列格式化、表单校验规则按类型分发；装饰器——高阶组件、Vue 的 mixin 思想；适配器——封装的 postUrl 就是适配不同端（pt/hz/wx）的接口差异；代理——v-model 本质、懒加载代理。我的观点：模式不是答案本身，是'代码在变好'的症状——项目里出现重复代码时，用模式重构，而不是为了用模式而写模式。面试时能说出'这个模式在我哪个组件里怎么用的'，比背十种定义有用。"

**答案要点：**
- 发布订阅（事件总线/EventBus，Vuex 的响应式本质也是观察者）、观察者（vue 响应式）。
- 单例（全局状态、axios 实例、地图实例）、工厂（创建 provider/组件工厂）、策略（表单校验、导出格式）。
- 适配器（接口适配，后端字段与前端结构映射）、装饰器（高阶组件 HOC / mixin / 指令增强）、代理（Proxy 响应式、事件委托）。
- 模板方法（基类封装流程，子类实现细节——表格基类）、职责链（表单校验链、中间件）。

**【项目案例】** ①**适配器**：`common.objToPostParam` 把前端嵌套对象序列化为后端 RPC 需要的 `a[0]=x&a[1]=y&b.c=z` 格式——典型的接口适配层；②**工厂**：aiChat 的 `createProvider('qwen'|'dify'|'deepseek')` 按配置创建不同 AI 厂商客户端；③**模板方法**：`BaseTable` 基类定义"加载→格式化→渲染→合计"流程，40+ 业务表只覆写数据源与列配置。这三个模式讲完，设计模式应用就立住了。

## 3-13. 数据结构与算法在前端（★★）

**详细回答（口述稿）：**
> "前端常用的数据结构：数组/对象存业务数据、Map 做字典和防重复（urlManager）、Set 去重、WeakMap 做深拷贝循环引用标记和缓存、树处理菜单和权限。算法高频的是：数组去重排序、扁平化、树转数组/数组转树（菜单）、防抖节流、字符串处理、二分查找和去重。项目里权限菜单就是树结构——后端返回层级菜单，前端递归转成路由表再 addRoute；地图轨迹点要做抽稀（减少点数）和时间排序。答这题我会强调：前端算法题的考察点是'用合适的数据结构简化问题'，比如查重用 Set、查映射用 Map，比在数组里 indexOf 遍历高效一个量级。"

**答案要点：**
- 常考：数组/链表/栈/队列/哈希表/树（二叉树遍历）/图（最短路径）/堆（TopK）。
- 应用：树（菜单、组织架构、递归渲染）、Map/Set（去重、缓存）、栈（括号匹配、撤销栈）、队列（消息、任务队列）、堆（排行榜 TopN）。
- 算法：排序（快排/归并）、二分查找、动态规划（简单）、字符串处理。
- 场景题：列表筛选去重、树转数组/数组转树、防抖节流本身也是"定时器 + 状态机"。

**【项目案例】** ①**数组转树**：`getAllWorkStore` 返回扁平的仓库/库区/库位列表，前端递归构建树供下拉与地图选择；②**树遍历**：菜单树按权限 `entityIds` 过滤后递归渲染；③**哈希表**：订单号 → 详情索引的 Map 缓存避免重复查询；④**栈**：地图轨迹回放的前进/后退。数据结构题配上这四个真实场景，说服力远超背概念。

## 3-14. 前端安全实践（★★）

**详细回答（口述稿）：**
> "前端安全我按威胁来源讲：XSS——脚本注入，防御靠转义输出、CSP、HttpOnly Cookie、小心 v-html；CSRF——伪造请求，防御靠 SameSite、自定义 token 头、Referer 校验；点击劫持——iframe 嵌套，防御靠 X-Frame-Options/CSP frame-ancestors；敏感信息泄露——密码别存 localStorage、日志别打印 token、HTTPS。项目里做了五件事：common.escapeHTML 转义富文本、登录态走内存+请求头、iframe 嵌入校验 event.origin 白名单、生产强制 HTTPS、敏感操作二次确认。我会总结：安全是'纵深防御'——前端做的是把攻击面缩小，但永远假设前端代码可被绕过，所以后端校验永远不能少。"

**答案要点：**
- XSS：转义输出、CSP、HttpOnly、避免 v-html 渲染用户输入。
- CSRF：SameSite Cookie、自定义 header token、Origin 校验。
- 敏感信息：token 不存 localStorage（XSS 可读）、生产 sourcemap 不上传、接口越权（前端权限只防君子，后端必须校验）。
- 供应链安全：`npm audit`、锁版本（package-lock）、私有源。
- 其他：点击劫持（frame 白名单）、暴力破解（验证码/限流）、依赖漏洞扫描。

**【项目案例】** ①token 存内存 + 每次请求头带 `Authorization`，页面刷新从 sessionStorage 恢复（两者权衡后选择可接受风险）②`iframe` 嵌入外部系统时校验 `event.origin === 'https://salary.1000e56.com'` 白名单③`vue.config.js` 关闭 productionSourceMap 上传 ④`v-entity` 前端权限 + 后端 `entityIds` 双重校验，前端只是体验层。

## 3-15. 移动端适配方案（★★）

**详细回答（口述稿）：**
> "移动端适配核心问题：不同屏幕宽度下 UI 等比缩放。主流方案三种：rem 方案——按设计稿宽度把 html 字号设成根字体大小，用 rem 单位，配合 postcss-pxtorem 自动转换，JS 监听 resize 更新根字号；vw/vh 方案——直接按视口比例，最直观；viewport meta + 固定宽方案——老式做法。项目里 H5 活动页和商城用的是 rem 适配：设计稿 750px，动态设置 html fontSize = clientWidth / 10，postcss-pxtorem 把 px 自动转 rem，字体和间距全部等比，跑不同机型不变形。我还会提一嘴：小程序和 uni-app 的 rpx 本质也是同一思想——按屏宽动态缩放。答完我会补一句：适配方案没有银弹，先问清楚'是内容型页面还是工具型页面'。"

**答案要点：**
- viewport 设置（`width=device-width, initial-scale=1`）。
- 方案一 **rem 适配**：`flexible.js` 动态算根字体（`html { font-size: clientWidth/10 }`），px → rem 用 postcss-pxtorem。
- 方案二 **vw/vh**：`1vw = 屏幕宽/100`，直接写 `font-size: 3.75vw`（375 设计稿 → 14px）；postcss-px-to-viewport 自动转换。
- 方案三 **响应式断点**（媒体查询）+ 弹性布局（flex/grid）。
- 注意：`1px` 物理像素问题（`transform: scale(0.5)` 或 border-image）、安全区（env(safe-area-inset-bottom)）、dpr 与图片清晰度（@2x/@3x）。

**【项目案例】** H5 活动页与微信端使用 **rem 适配**（`postcss-pxtorem` + 设计稿 750），配合 `viewport-fit=cover` 处理 iPhone 刘海屏安全区；小程序端用 rpx（750rpx = 屏宽）同一套设计稿两处落地的经验证明了对适配体系的理解。老平台 PC 端则用固定 1280 栅格 + 兼容 IE11。

## 3-16. 前端缓存策略（★★）

**详细回答（口述稿）：**
> "前端缓存策略我从两层讲：HTTP 层——强缓存 Cache-Control 加协商缓存 ETag/Last-Modified；应用层——localStorage 存低频大对象、IndexedDB 存结构化数据、Service Worker 做离线缓存和资源预缓存。关键认知是'缓存一致性'：带 hash 的资源可以放心长缓存（改了就换 URL），HTML 必须 no-cache 保证拿到最新页面。项目里的完整策略：js/css 文件名带 contenthash 一年强缓存 + gzip；HTML no-cache；登录态、权限这种敏感数据不走浏览器持久缓存，用内存；字典数据短缓存减少重复请求。我会强调：缓存策略要和发布策略配套设计——先设计'内容寻址'的发布，才能放心开长缓存。"

**答案要点：**
- HTTP 缓存（强缓存/协商缓存）+ 浏览器存储（localStorage/sessionStorage/IndexedDB）+ 内存缓存（Promise 结果、计算缓存）。
- 静态资源：hash 文件名 + 长缓存；HTML：no-cache。
- 数据缓存：字典表、权限、用户信息 localStorage/IndexedDB 缓存，接口带版本号失效。
- Service Worker 缓存（PWA）：离线可用、网络拦截。
- 更新策略：版本号对比（缓存 key 带 version）、`etag`、发布时资源 hash 变化天然失效。

**【项目案例】** ①字典数据 `getSysStaticData` 结果缓存到 localStorage（key 带版本号，发布时 bump 版本失效重拉）——字典接口调用从每次进页面都拉降到一天一次；②`excelOut`/`lodop` 动态 import 后浏览器缓存 chunk；③登录态 7 天会话用 localStorage 存 `sessionTime`，超 4 小时未操作强制重新登录——缓存策略和会话安全配合。

## 3-17. 首屏加载优化（★★★）

**详细回答（口述稿）：**
> "首屏优化我按'加载链路'从外到内讲：网络层——CDN 加速、HTTP2 多路复用、gzip；资源层——路由懒加载、组件按需引入、图片压缩 WebP + 懒加载、去掉阻塞渲染的 CSS/JS；渲染层——骨架屏减少白屏、首屏数据接口合并或并行、预取关键资源；代码层——控制主包体积、按需 polyfill。项目里三板斧：40+ 页面全路由懒加载、Element UI 按需引入、大屏独立 chunk，主包从 4.2MB 降到 1.1MB，首屏从 3 秒多降到 1.5 秒内。衡量指标用 Lighthouse 的 FCP/LCP。答这题我会先问面试官'是 ToC 还是 ToB 系统'——内部系统首屏要求没那么苛刻，优化要按 ROI 排优先级。"

**答案要点：**
- 指标：FCP/LCP/白屏时间；核心手段排序：
  1. 路由懒加载 + 按需引入（最有效）
  2. gzip/Brotli 压缩
  3. CDN 分发静态资源
  4. 骨架屏/loading 占位（感知优化）
  5. 压缩图片、小图 base64
  6. 公共库 CDN 外链（谨慎，注意可用性）
  7. preload 关键资源、prefetch 次要资源
- 分析工具：Lighthouse、webpack-bundle-analyzer、`performance.timing`。

**【项目案例】** 平台首屏优化实测数据：主包 4.2MB（gzip 前）→ 1.1MB；首屏 6s+ → 2s 内。手段：①Element UI/Vant 按需引入 ②40+ 页面路由懒加载拆 chunk ③gzip ④登录页独立小包 ⑤骨架屏（登录后菜单区）。可量化 = 面试最有说服力的部分。

## 3-18. 虚拟滚动与大数据渲染（★★★）

**详细回答（口述稿）：**
> "虚拟滚动的核心思想：只渲染可视区内的行，总数据再多 DOM 数量恒定。实现三个关键：可视高度 / 行高算可见行数，加 overscan 缓冲避免白屏；监听滚动把 startIndex 换算成偏移，容器内绝对定位；滑动时用 transform 平移而不是重排。两个坑要提：行高不固定时要用'预估行高 + 渲染后校正'；滚得太快要 rAF 节流。项目里订单表格和货主端列表用了类似思想：服务端分页 + 按需渲染，5 秒轮询的大屏也是增量更新 DOM。答这个题我会强调：虚拟滚动是'大数据量 + 固定容器高度'的标配解，但先评估——如果服务端分页能满足，就不必上，复杂度是代价。"

**答案要点：**
- 问题：一次性渲染几千行表格/列表 → DOM 过多 → 长任务阻塞主线程、内存暴涨。
- 方案层次：
  1. **分页**（服务端/前端）：最简单，但不满足"连续滚动"体验。
  2. **虚拟滚动**：只渲染可视区 + 缓冲区的行，用 `padding`/`transform` 撑起总高度；核心 = 容器高度 / 行高 → 起始索引与结束索引 → 切片渲染；注意行高固定（`itemSize`），动态行高需预估 + 校正。
  3. 时间分片（requestIdleCallback 分批插入）。
- 代表库：vue-virtual-scroller、@tanstack/virtual；vxe-table 内置虚拟滚动。
- 关联：图表大数据用 canvas 而非 DOM 也是同一思路。

**【项目案例】** 项目订单列表选的是"**服务端分页（每页 20）+ 快速筛选**"而非虚拟滚动——理由：业务上用户不需要一次看 10 万行，筛选到百行以内体验更好；而车辆监控大屏同时展示数百辆车实时轨迹，用 canvas 绘制而非 DOM 标记，内存稳定在百 MB 内。面试要讲清楚"**按场景选方案**"，而不是背"虚拟滚动很牛"。

## 3-19. 前端测试（★）

**详细回答（口述稿）：**
> "前端测试分三层：单元测试测函数和组件（Jest + Vue Test Utils，重点测工具函数、组件 props/emit）；集成测试测组件间交互；端到端测真实用户流程（Cypress/Playwright）。成本排序：单元 < 集成 < E2E。我的实践观：工具函数、权限逻辑、格式化、请求封装这些'纯逻辑'必测——性价比最高；页面级 E2E 挑核心链路测，比如登录、下单、权限拦截，别追求全覆盖。项目里为 `common.js` 的类型判断、格式化、深拷贝写了单测；表格组件测了 props 变更和分页触发。答这题我会说实话：团队按 ROI 分层投入，不是所有代码都要测，但'核心逻辑无测试'是底线问题。"

**答案要点：**
- 单元测试：Jest/Vitest + @vue/test-utils，测纯函数/组件 props/事件。
- 组件测试：挂载组件断言渲染、交互、快照。
- E2E 测试：Cypress/Playwright，走完整用户流程。
- 测试金字塔：单测多、集成中、E2E 少。
- 实践建议：核心工具函数与复杂组件必测；业务页抽离逻辑层（纯函数）再测。

**【项目案例】** 项目对 `common.js` 的核心纯函数（`objToPostParam` 参数序列化、`formatDate`、防抖节流、金额千分位）写了 Jest 单测，参数序列化这类"格式强约定"函数一旦回归会全项目报错，必须测试兜底；业务页面则以人工回归 + 大屏自动化截图对比为主，性价比优先。

## 3-20. Git 协作与版本管理（★）

**详细回答（口述稿）：**
> "Git 协作我讲两件事：分支模型和提交规范。分支模型我们用主干 + 功能分支 + release 分支：功能开发切 feature 分支、开发完合并回 develop、发版切 release 分支走测试、测试通过合并 master 打 tag，线上 bug 用 hotfix 分支修复后同时合并 master 和 develop。提交规范用 commitlint 约定 `feat/fix/docs/refactor` 前缀，配合 husky pre-commit 跑 lint。实际用的高频操作：rebase 保持分支干净、cherry-pick 挑提交、revert 回滚。项目里多端多团队并行开发，靠这套模型避免互相踩代码，历史可追溯。答这题我会补一句：分支模型没有绝对正确，核心是'小步提交 + 可回滚 + 代码评审'三个习惯。"

**答案要点：**
- 分支模型：Git Flow（master/develop/feature/release/hotfix）vs GitHub Flow vs GitLab Flow；团队小用简化版。
- Commit 规范：`feat/fix/docs/style/refactor/perf/test/chore`（Conventional Commits），配合 changelog 自动生成。
- 操作：rebase（线性历史）vs merge（保留合并记录）；cherry-pick；stash；reflog 恢复。
- Code Review：MR/PR 流程、机器人检查（lint/deps）、2 人以上评审。
- 保护：master 禁止直推、分支保护规则、签名提交（可选）。

**【项目案例】** 项目分支规范：`feature/xxx` 开发 → MR 到 `develop` → 预发布 `release/x.y.z` → 打 `tag` 发版；commit 全部带 `fix(订单): ...` 前缀；版本号随 `ci.sh` 自动 bump 并写入 `build.json`。面试可补充：曾用 `git bisect` 在 200+ commit 中二分定位到导致打包产物异常的某次配置改动——排查思路比命令本身更值钱。
