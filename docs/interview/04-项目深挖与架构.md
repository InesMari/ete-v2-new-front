## 4-2. 多租户 SaaS 架构怎么实现？一套代码如何跑 5 个端？（★★★）

**详细回答（口述稿）：**
> "这套架构的关键是'入口分流 + 状态驱动'。第一步，App.vue 的 init() 做双重识别：看 hash 路由 path——`/hz` 是货主端、`/edu` 是大学端、`/wxOrder` 是微信下单、`/ahresty` 是车辆监控；再看域名——`hz.1000e56.com` 走货主登录、`edu.1000e56.com` 走大学登录，其他走平台。第二步，识别结果写入 Vuex 的 componentName。第三步，模板里用 `<component :is="componentName">` 动态渲染对应端的入口组件，配合 keep-alive 缓存。第四步，入口组件内部按角色调后端拿菜单，路由用 myTab 的 addRoute 动态注册。好处是一个仓库、一次构建、统一发版，各端共享 common.js 和组件库；代价是入口层和权限判断要精心设计，避免端与端互相干扰。"

**答案要点：**
- **入口分流**：`App.vue` 的 `init()` 双重识别：①按 hash 路由 path 判断（`/hz` → 货主端、`/edu` → 大学端、`/wxOrder` → 微信下单、`/ahresty` → 车辆监控等）②按域名 host 判断（`hz.1000e56.com` → 货主登录、`edu.1000e56.com` → 大学登录，其余 → 平台），最终写入 Vuex `componentName` 状态，由 `<component :is="componentName">` 渲染对应端入口。
- **独立构建**：同一源码通过 `vue.config.js` 多入口配置，产出 5 个独立 SPA（各端只打包自己路由可达的页面 chunk）。
- **接口归一**：所有端统一走 `common.postUrl(beanName, methodName, params)` 的 RPC 调用，后端按租户 + 登录态返回隔离数据；`entityIds` 权限数组控制功能可见性。
- **特殊路径**：`/ahresty`（车辆监控）、`/appointmentBoard` 等大屏页面、`/fileViewer` 文件预览在 App.vue 单独识别、独立挂载，不进入业务端壳子。
- **https 强化**：`http → https` 自动跳转；iframe 嵌入外部系统用 `postMessage` + `origin` 白名单通信。

**【项目案例】** 引用真实机制：`<component :is="componentName">` + Vuex 状态驱动入口；`router.addRoute` 按菜单动态注册各端路由；`loadEntityIds` 登录后拉权限写入 `localStorage.entityIds`。这套"一壳多端 + 动态路由 + 统一 RPC"是 SaaS 平台前端架构的标准答案。

## 4-3. 你们的 postUrl 请求封装是怎么设计的？为什么叫"RPC 风格"？（★★★）

**详细回答（口述稿）：**
> "postUrl 是我们请求层的统一入口，签名是 `postUrl(beanName, methodName, params, successFn, errorFn, type, shadow)`。叫 RPC 风格是因为它不像 REST 按资源组织 URL，而是'调后端的方法'——beanName 是服务对象，methodName 是方法名，前端传参数，后端执行方法返回结果，本质就是远程过程调用。封装做了五件事：统一 Promise 化，成功 resolve 失败 reject；参数序列化，支持后端要求的 `key[i]`、`key.subKey` 格式；防重复请求，`urlManager` 维护 Map，同一接口 pending 期间返回同一个 Promise；统一错误处理，业务码和非业务码分开，403 自动跳登录；下载场景支持 blob 和 excelOut 动态导出。全项目 1764 个接口调用点，没有一个散落 try/catch——这就是封装的价值。"

**答案要点：**
- 调用方式：`postUrl(beanName, methodName, params, successFn, errorFn, type, shadow)`——像调本地函数一样调后端服务，`beanName` 是服务名、`methodName` 是方法名，与后端 Dubbo/HTTP 服务一一对应。
- 内部实现（`src/utils/common.js`）：
  - 基于 `XMLHttpRequest` 包一层 Promise，成功 `resolve`、失败 `reject`。
  - **参数序列化**：`objToPostObj/objToPostList` 把嵌套对象/数组转成 `key[i]=value`、`key.subKey=value` 的扁平参数，适配后端 RPC 参数格式。
  - **防重复请求**：`urlManager` 记录进行中的请求，同一 URL 未返回前再次调用直接复用 Promise，防止表格连点/多 Tab 重复提交。
  - **统一状态码**：200 → 成功回调；403 → 提示后 30 秒跳登录；500 → 提示刷新；501 → 业务错误 Message。
  - **会话记录**：请求时更新 `sessionTime`，超过 4 小时未活动强制重新登录（配合 7 天记住登录）。
  - `shadow` 参数控制是否显示遮罩 loading。
- 收益：1764 个接口调用全部走同一通道，鉴权、错误处理、防重复、遮罩、日志一处在 20 分钟内全项目生效。

**【项目案例】** 面试可现场画调用链：页面方法 → `postUrl('orderService','queryOrderInfoList',{page,rows})` → 序列化 → XHR → 后端 → 回调更新表格。再补一句"后来在这个封装上加 `responseType:'blob'` 支持导出下载、加 `sendBeacon` 上报错误"，体现演进思维。

## 4-4. 你们怎么实现动态路由？权限菜单是怎么来的？（★★★）

**详细回答（口述稿）：**
> "动态路由的标准链路是：登录 → 后端返回当前用户的菜单树 → 前端把菜单转成路由配置 → `router.addRoute()` 注册 → push 跳转。项目里这个逻辑在 myTab 组件里：它拿到后端菜单项，对每个菜单执行 `router.addRoute({ path, name, component: () => import('@/page' + item.urlPath) })`，同时缓存路由名到权限集合，这样未授权的菜单根本不在路由表里，URL 直敲也 404。组件用懒加载，页面 chunk 按需加载。有个工程细节：webpack 动态 import 的 chunk 有时会加载失败（部署期间请求旧 chunk），我们在全局捕获 'Loading chunk failed' 错误，提示用户刷新而不是白屏。答这题我会强调：权限菜单做到'后端下发 + 前端动态注册 + 路由级守卫'三层，才算完整。"

**答案要点：**
- 登录后调 `loadMenuTree/queryUserMenuLabelData` 拿当前用户的菜单树（后端已按权限过滤），存 Vuex。
- `myTab` 组件遍历菜单，对每个菜单项执行 `router.addRoute({ path, name, component: () => import('@/page' + item.urlPath) })` 动态注册，再 `router.push` 打开首个页面。
- **懒加载 + chunk 失败处理**：页面组件全部动态 import 分包；监听路由错误捕获"`Loading chunk .* failed`"，提示"系统有更新，是否刷新"，避免用户卡在白屏。
- Tab 页签：打开过的页面以页签展示，支持右键刷新/关闭、`vuedraggable` 拖拽排序、query 参数在 urlPath 中解析。
- 权限与路由的关系：**菜单即路由**——后端给什么菜单，前端就注册什么路由，天然实现"未授权页面无法访问"。

**【项目案例】** 引用 `myTab.js`：`openTab` 里 `urlPath.split('?')` 拆路径与 query → `addRoute` → `push`；`Loading chunk failed` 用 `window.location.reload()` 加 `confirm`。这比"写死 router 表"更适合 SaaS：新页面加菜单即上线，前端零改动。

## 4-5. 你们的权限体系是怎么设计的？（★★★）

**详细回答（口述稿）：**
> "权限体系我分三层讲。第一层路由权限：登录后按用户角色从后端拿菜单树，动态注册路由，没权限的菜单根本不在路由表里，直敲 URL 也进不去。第二层页面元素权限：用自定义指令 `v-entity`——登录时把权限 ID 数组写进 localStorage 的 entityIds，模板里 `<el-button v-entity="'order:add'">`，指令发现值不在数组里就 `el.remove()` 直接移除元素；`v-entitys` 支持多权限'或'匹配，命中一个就放行。还有个动态映射细节：`:entityId="[{1:101,2:202},pId]"` 按路由 pId 从映射表取权限值，同一个按钮在不同菜单页对应不同权限点。第三层后端兜底：前端权限只是体验层，接口层每次请求都校验 token 和权限。我总结：权限是'菜单、按钮、接口'三管齐下，前端做显隐，后端做校验。"

**答案要点：**
- 三层：
  1. **接口层**：后端按登录用户 `entityIds`（权限点 ID）鉴权，前端 token 头部携带。
  2. **路由/菜单层**：菜单由后端按权限下发，前端动态注册（见 4-4）。
  3. **元素层**：`v-entity`/`v-entitys` 自定义指令控制按钮/字段显隐。
- `v-entity` 实现（`src/utils/directive.js`）：`binding.value` 传入权限 id，指令读取 `localStorage.entityIds`（逗号分隔串）为权限数组，value 不在数组中则 `el.remove()` 直接移除元素；`v-entitys` 把 value 按逗号拆成 Set，任一命中即放行（"或"匹配）；还支持动态权限 `:entityId="[{1:101,2:202},pId]"`——按当前路由 `query.pId` 从映射表取值，实现"同一按钮在不同菜单页映射不同权限点"。
- 前端权限是体验层，后端必须二次校验——安全边界在后端。
- 扩展：同一指令还衍生出数字输入校验（`mynumval` 只能输整数、`mypmnumval` 百分比）等 DOM 能力指令。

**【项目案例】** 典型页面示例：订单操作列有"打印面单（entityId=1001）""取消订单（1002）"，管理员登录看到全部，普通客服登录按钮直接被指令移除——用户看到的就是他能做的，体验干净。面试重点讲"为什么用指令而不是 v-if"：指令面向 DOM 操作、可跨组件复用、初始化/更新钩子天然契合权限变更。

## 4-6. 你们怎么解决大数据量渲染的性能问题？（★★）

**详细回答（口述稿）：**
> "这个问题我们的解法是分层治理，不是一招走天下。第一层：优先服务端分页——业务列表能分页就不一次拉全量，每页 20 条，查询是'替换型'更新，用分页组件天然可控。第二层：对无法分页的看板场景，用增量渲染——大屏 5 秒轮询的数据不重建整表，只更新变化行的 DOM。第三层：极端情况上虚拟滚动思路——表格容器固定高度，只渲染可视区行，加 overscan 缓冲。除此之外配套优化：Object.freeze 冻结不参与渲染的大字典数据，减少响应式劫持开销；格式化放 computed 缓存，避免重复计算。讲效果：订单大列表从加载 3 秒、滚动掉帧，优化到秒级打开、滚动流畅。这个题我会强调：性能问题先量化定位，再选方案，分页能解决的绝不上虚拟滚动。"

**答案要点：**
- 问题定位：①一次性渲染几千行 DOM → 主线程长任务阻塞、首屏卡顿 ②接口一次性返回大数组 → 网络与内存压力 ③图表几千个节点。
- 解决组合拳（按场景选型）：
  1. **服务端分页 + 筛选**（订单/库存列表）：每页 20 条，条件查询，把"大数据"变"小数据"。
  2. **`Object.freeze` 冻结只读字典**：字典数据不参与响应式劫持，省掉 defineProperty 递归的开销。
  3. **canvas 渲染**（车辆监控/大屏）：数百辆车实时轨迹用 canvas 绘制，替代 DOM 标记。
  4. **`requestIdleCallback` 分批插入**（首屏表格）：空闲时间分片渲染行，避免长任务。
  5. **长列表虚拟化**：需要连续滚动浏览大列表时用虚拟滚动（本项目列表以分页为主，虚拟滚动作为备选方案说明）。
- 指标验证：FPS 稳定 60、内存稳定、交互延迟 <100ms。

**【项目案例】** 最典型的例子是**车辆监控大屏**：同时展示 300+ 辆车的实时位置，如果用 DOM 标记会直接卡死；改用 canvas 分层绘制（底图 + 车辆层 + 轨迹层），配合 5s 轮询增量更新，帧率稳定。面试讲"先量化瓶颈 → 按场景选方案 → 用数据验证"的完整方法论。

## 4-7. 你自研的组件库有哪些？怎么保证复用性和可维护性？（★★）

**详细回答（口述稿）：**

**答案要点：**
- 规模：40+ 公共组件，覆盖 5 类：

  - 表单类：`mySelect`/`mycity`（省市区）/`myImport`（导入）/`dataPicker`/`areaMatch`。
  - 布局与导航：`myTab`（页签 + 动态路由）、`tree`/`treeV2`（树形控件）、`navMenu`。
  - 业务组件：`mapTrack`（地图轨迹回放）、`mapDialog`（地图选点/圈选）、`printSet`（Lodop 打印）、`file-viewer`（文件预览）、`commonOpLog`（操作日志）、`videoPlayer`。

- 复用保障：

  3. **文档驱动**：每个组件有使用示例与 props 说明（`docs/web-02-公共组件库.md` 47 组件）。
  4. **版本收敛**：新增需求先看组件库，避免"每个页面自己写一套"。
- 成果：业务页从"写页面"变成"拼组件"，订单相关页面 7 条以上业务线共用同一套列表/表单组件，开发效率提升 40%。

**【项目案例】** 举 `tableCommon`：业务页传入 `head`（列配置数组：字段、标题、宽度、formatter、合计）与 `load` 函数即可获得完整表格（分页、多选、导出、行操作插槽）。新业务线接订单系统，2 天完成列表页——这就是组件化红利。

## 4-8. 地图轨迹回放是怎么实现的？（★★）

**详细回答（口述稿）：**
> "轨迹回放用百度地图实现，核心是'数据 + 播放器 + 渲染'三部分。数据：后端返回车辆的轨迹点数组，含经纬度、时间、速度，前端先做抽稀（去掉冗余点，点数从几千压到几百）和按时间排序，再计算总里程、平均速度。播放：用 BMap 的驾驶路线类或自己做定时器按时间推进——我们用的是路书播放，支持播放/暂停/进度条拖动，拖动时把 marker 定位到对应时间点。渲染：Polyline 画轨迹线，起点终点 marker 区分，超速段标红、停留点画标记；播放中 marker 沿轨迹移动，车头方向用 rotate 跟随航向。还要处理地图视野自动跟随。我补充工程细节：组件销毁时清理所有覆盖物和事件，防止地图实例内存泄漏；WebView 混合上传和地图 js 加载失败都有兜底。这个组件在车辆监控和运输调度两个业务线复用。"

**答案要点：**
- 技术选型：百度地图 BMap（PC 端），车辆监控用 canvas 叠加；小程序端用腾讯地图 + 原生 map 组件。
- 实现步骤（`src/components/mapTrack/mapTrack.js`）：
  1. 调 `monitorTF.locationHis({ waybillId })` 拿到轨迹点数组 `locationList` + 工作点 `workList` + 运单信息。
  2. `new BMap.Map` 初始化地图，`polyline` 画轨迹线，`setViewport` 自适应视野。
  3. **路书播放**：按 `speedPlan`（播放倍速）定时移动 marker，逐点推进，可暂停/继续；剩余里程 `distancePlan` 实时计算。
  4. **超速分析**：遍历相邻点算速度，超过阈值（50/60/80/100）的片段标记红色 + 列表展示。
  5. **停留分析**：相邻点间隔超 10 分钟标记"停留"，按停留时长（10min~6h）分级展示。
  6. 覆盖物清理：切换/销毁时清除 Polyline/Marker，防内存泄漏。
- 关键难点：轨迹点几千个时绘制性能（抽稀 + 只画视野内）、时间轴联动、倍速播放的动画帧管理。

**【项目案例】** 面试可画"数据流"：waybillId → locationHis → 坐标数组 → 画线 + 播放器 + 超速/停留双列表。再提一句"超速规则是业务配置（不同线路限速不同），前端从接口拿规则表动态生成阈值"，体现与业务结合的深度。

## 4-9. 打印和导出是怎么做的？（★★）

**详细回答（口述稿）：**
> "打印这块分两类场景。一类是标签、单据打印，用 Lodop 控件——它是最成熟的 web 打印方案，通过安装客户端插件实现精确套打。我们封装了 printSet 组件做打印机管理：检测控件是否安装、选择打印机、设置纸张尺寸和边距，然后按单据模板生成打印内容，模板里处理分页、条码、重复表头。一类是通用页面打印，用 `window.print()` 配合 `@media print` 样式，打印时只显示内容区。导出走两条路：数据量小用前端导出——blob 下载 Excel；大数据量走后端导出——后端生成文件返回 URL 或流。项目里封装了 excelOut 工具，统一处理列头、字段映射、日期格式化、文件名编码。我总结：打印导出的关键不在技术多炫，在于'模板和格式要跟业务单据一致'，所以封装时把格式配置外置，业务改格式不动代码。"

**答案要点：**
- **打印（Lodop）**：`printSet` 组件调用 `lodopUtil`——`queryPrintDevices` 列出本机打印机、按业务类型（面单/订单/报表）选择模板；核心是用 Lodop 控件的 `ADD_PRINT_*` 方法拼版面，浏览器端直连打印。为什么不用 `window.print()`：物流面单需要精确到毫米的排版 + 连续多联纸 + 打印机选型，浏览器打印无法满足。
- **导出 Excel**：`excelOut.js` 基于 `xlsx` 库的 `export_json_to_excel`，动态 `import('@/utils/excelOut')` 按需加载，不污染首屏；支持多 sheet、表头合并、列宽。
- **下载文件**：`common.js` 里 blob 方式——`responseType:'blob'` + `URL.createObjectURL` + `a.download` + `revokeObjectURL` 释放。
- 兼容性处理：Lodop 需要装客户端控件，组件内置"未安装引导"；导出大文件用 loading 遮罩防连点。

**【项目案例】** 典型业务：货主端打印"入库预约单"与"运单回单"，选择打印机后 2 秒出单；平台端导出万行账单 Excel 走 blob + 流式下载，导出期间遮罩防重复。面试强调"**按场景选技术**"：通用网页用浏览器打印，物流单据用 Lodop，导出必须防内存与防连点。

## 4-10. 大屏看板是怎么实现的？（★★）

**详细回答（口述稿）：**
> "大屏看板我们做了 6 个：订单看板、预约看板、仓储中心看板、今日计划、配送看板、车辆监控。技术方案是三块拼起来的：数据层用轮询——mounted 启动 setInterval 每 5 秒拉一次数据，beforeDestroy 清理，为避免请求堆积加节流；图表层用 ECharts，canvas 渲染大数据量不卡；布局层用 CSS Grid 或绝对定位的网格布局，1920x1080 基准做等比缩放适配不同分辨率大屏。几个工程细节：一是数据刷新要平滑，新旧数据交替用过渡动画，避免整个大屏闪；二是大屏独立路由、独立 chunk，不跟业务主包混在一起；三是断网或接口失败要有降级提示，不能黑屏；四是按不同角色显示不同指标。我讲这个题会强调：大屏的核心是'数据和图表的联动'，以及'长时间运行的稳定性'——我们跑了一个月不重启没内存泄漏。"

**答案要点：**
- 场景：仓库预约、订单调度、仓储中心、今日计划、配送、车辆监控等 6+ 大屏。
- 技术栈：ECharts（图表）+ 全屏自适应布局（rem/百分比 + resize 监听）+ 定时轮询。
- 实现细节：
  - **数据刷新**：`setInterval` 每 5s 调看板专用接口（`queryWmsAppointInfoPage`、`queryHomeCollectData`、`queryHomeInStokeData`、`queryHomeOutStokeData`、`queryOrderListForScreen` 等），`$nextTick` 后更新图表。
  - **动画**：滚动列表用 `transform: translate3d` 合成层动画，避免重排；ECharts 用 `setOption` 增量更新而非重建实例。
  - **自适应**：`window.resize` 节流后 `chart.resize()`；多屏投放按 16:9 基准缩放。
  - **稳定性**：轮询失败重试、接口防抖（节流刷新函数）、页面隐藏时暂停轮询（`document.hidden` 判断），节省资源。
- 与 WebSocket 的取舍：轮询实现简单、与统一 HTTP 网关一致、可接受 5s 延迟；秒级实时才上 WebSocket。

**【项目案例】** 预约看板：货主在 hz 端提交预约 → 看板 5s 内滚动展示待处理预约 → 仓库人员点"接单"处理。面试讲"看板不是花哨图表，是业务环节的实时窗口"，并把大屏按业务场景分类，比只背 ECharts API 高级得多。

## 4-11. 你们项目做过哪些性能优化？量化结果？（★★）

**详细回答（口述稿）：**
> "性能优化我按两个维度汇报成果。加载性能：首屏从 6 秒优化到 2 秒。手段是路由全量懒加载、Element UI 按需引入、组件级懒加载、gzip、公共库 CDN 和缓存，主包从 4.2MB 降到 1.1MB。运行性能：大数据表格从卡顿到流畅。手段是服务端分页 + 增量渲染 + 虚拟滚动思路 + Object.freeze 冻结大字典 + computed 缓存。开发性能：构建从 90 秒压到 40 秒，靠 babel 缓存、多线程编译、缩小 loader 范围。还有个细节：监控——我们对接口做了耗时统计，发现并推动了后端把慢查询接口的响应从 2 秒压到 300ms。我总结：性能优化永远先量化定位再动手，优化的效果要能说出数字，这是和普通前端的区别。"

**答案要点：**
- 首屏：路由懒加载 + 按需引入 + gzip + CDN → 首屏 6s+ → 2s 内；主包 4.2MB → 1.1MB。
- 渲染：分页列表、Object.freeze 字典、canvas 大屏、transform 动画、事件委托。
- 请求：postUrl 防重复请求、字典数据 localStorage 缓存、Promise.all 并行、轮询节流。
- 构建：splitChunks 拆 vendor、压缩去 console、产物分析。
- 网络：HTTP/1.1 keep-alive、资源带 hash 长缓存、HTML no-cache。
- 度量方法：Lighthouse 打分、Performance 面板、`performance.timing` 埋点。

**【项目案例】** 讲一个"被逼出来的优化"最有说服力：老客户使用旧车载终端（低端机型 + 弱网），大列表一度白屏 8s；针对性做了列表分页 + 图片懒加载 + 弱网重试 + 骨架屏后，客户反馈"明显变快"。**性能优化绑定业务场景与用户反馈**，比罗列手段更打动人。

- 与原生小程序共存：老功能原生维护、新功能 uni-app 渐进迁移，避免大爆炸重构。
- 发布：uni 云打包 App，小程序上传各平台；CI 里 cli 模式可自动构建。

## 4-14. 微信支付、地图、混合上传这些端上难点怎么攻克的？（★★）

**详细回答（口述稿）：**
> "这三个都是小程序端能力的硬骨头，我各讲一个攻克过程。微信支付：支付必须后端统一下单拿 prepay_id，前端调 `wx.requestPayment`，难点是签名和回调时序——我们设计了'下单成功 → 调起支付 → onShow 里查订单状态'的状态机，防止支付成功但页面没刷新、用户反复点击重复下单。地图：定位要处理授权拒绝的降级（经纬度 + 地址互转），路线规划要拼接途经点，轨迹回放要把坐标点按时间排序并抽稀，覆盖物要按视角聚合否则几十个 marker 卡顿。混合上传：小程序里的 `web-view` 嵌 H5，H5 里要调小程序的原生能力（拍照、上传、地图选点）——用 `wx.miniProgram.postMessage` 和 `navigateTo` 双向通信，还得处理 H5 与小程序的登录态同步。我总结：端能力攻坚的共同方法论是——先摸清平台限制，再做兼容设计，最后加状态机和降级兜底。"

**答案要点：**
- **微信支付**：统一下单（后端下单拿 prepay_id）→ 前端 `wx.requestPayment` 拉起收银台 → 支付回调验证。注意：金额单位分、签名、回调验签在后端；前端只负责拉起与结果轮询，**绝不信任前端金额**。
- **地图**：`wx.getLocation` 授权处理（拒绝后引导设置页）、`wx.openLocation` 调起导航；轨迹回放用 map 组件的 polyline + `include-points` 自适应。
- **WebView 混合上传**：小程序 `web-view` 组件嵌入 H5，H5 侧用 `JSSDK` 调小程序能力（`wx.miniProgram.navigateTo`）；大文件通过小程序端 `wx.uploadFile` 直传，规避 H5 在 web-view 内上传受限；加本地压缩 + 分片。
- 踩坑：iOS/安卓定位权限差异、小程序基础库版本兼容（`wx.canIUse` 判断）、支付回调延迟用"轮询订单状态"兜底。

**【项目案例】** 司机端"到货拍照回单"完整链路：H5 页面调用 `wx.miniProgram.postMessage` 通知小程序 → 小程序 `wx.chooseMedia` 选图 → canvas 压缩 → `wx.uploadFile` 直传 OSS → 回传 URL → H5 展示。面试用一条链路讲清"小程序与 H5 的能力边界与协作"，很能体现端上经验。

## 4-15. 你怎么把 AI 接进传统 SaaS 系统？（★★）

**详细回答（口述稿）：**
> "这个项目是我在传统 SaaS 里做 AI 落地的完整闭环，我分四步讲。第一步选底座：我们选了 Dify 做 LLM 应用平台，模型接通义千问，Dify 负责工作流、知识库、提示词这些 AI 侧的事，前端不直接碰模型 API。第二步做知识库：把物流业务文档（运单规则、常见问题、政策）切块向量化，建 RAG 检索，回答时先检索再生成，保证答案基于公司知识而不是模型瞎编。第三步打通业务：AI 输出不只是文本——我们会约束 Dify 输出结构化 JSON，前端解析后直接执行真实业务操作，比如智能调度给 AI 一个订单列表，它输出调度建议 JSON，前端解析成表单回填并调接口提交。第四步做交互组件：Vue3 的 aiChat 组件支持流式输出、多会话管理、工具调用。这个项目的价值是：它证明了 AI 不是'套壳聊天'，而是能真正驱动业务流程。"

**答案要点：**
- 场景：物流知识库问答（司机/客服自助查规则）+ 智能调度（AI 输出操作 → 前端执行 → 回传结果）。
- 架构（`src/page/demo/aiChat`）：
  - **provider 抽象**：`createProvider('qwen'|'deepseek'|'dify')` 统一不同模型厂商的 API（chat completions / SSE 流式 / Dify 对话）。
  - **流式输出**：`fetch` + `ReadableStream` 逐段解析 SSE，边收边渲染，支持 `AbortController` 停止生成。
  - **多会话**：`sessions` 数组 + `currentSessionId`；Dify 场景用 `conversation_id` 映射保持多轮上下文。
  - **工具调用闭环**：AI 输出结构化 JSON → `agentRouter` 解析 → 调业务接口（`difyExecutor.registerDefaultInterfaces` 白名单）→ 结果回填对话。
  - **对话渲染**：markdown 渲染 + 流式打字机效果（typeDelay 逐字）。
- 落地注意：模型幻觉 → 用 RAG（知识库检索）约束答案来源；敏感操作 → 白名单接口 + 人工确认；成本 → Token 计数 + 缓存 + 模型分级。

**【项目案例】** 智能调度 Demo 完整链路：用户说"帮我查今天北京到上海的订单"→ Dify 工具调用 → 前端执行 `queryOrderInfoList` → 结果回填 → AI 汇总成表格文字。面试讲"**AI 不是聊天玩具，是可控的业务执行器**"，白名单 + 结构化输出 + 人工确认是关键词。

## 4-16. 你们从 0 到 1 搭前端工程是怎么做的？（★★）

**详细回答（口述稿）：**
> "从 0 到 1 我按'地基三件套'讲：工程底座、请求层、通用能力。工程底座：Vue CLI + 多入口配置（一个仓库出 5 个端）、目录规范（按端/模块/组件分层）、ESLint + Prettier + husky 强制规范、alias 统一路径。请求层：postUrl 的 RPC 封装 + 统一错误处理 + token 管理 + 防重复请求，这是所有业务的地基，先定接口契约再写页面。通用能力：权限指令、动态路由 myTab、40+ 自研组件逐步沉淀。顺序上很关键：我先定'多租户入口'再定'请求层'，因为所有页面都依赖这两个；组件库是边做业务边沉淀的，不做闭门造车。最后配上文档（web-README、api-00 接口文档）。我的理念：从 0 到 1 不是把框架跑起来，而是把'规范 + 基建 + 沉淀机制'一起搭好，后面的人写代码才有章法。"

**答案要点：**
- 脚手架：Vue CLI（老）/ Vite（新），统一 Node 版本（.nvmrc）+ 包管理（package-lock 锁版本）。
- 目录规范：`src/page/{端}/{业务域}/页面` 三级目录 + `components/`（公共） + `utils/`（工具）+ `store/`（全局状态）。
- 三件套固化：ESLint + Prettier + Husky（提交前 lint）；`editorconfig` 统一编辑器。
- 请求层：postUrl 封装（鉴权/错误/防重/遮罩）一次到位。
- 路由与权限：动态路由 + v-entity 权限体系（见 4-4/4-5）。
- 配置管理：`vue.config.js` 多端入口、代理、CDN、打包优化；环境变量（`.env.development/production`）。
- 文档：开发规范（命名、三文件模式、接口约定）+ 组件库文档，新人 1 周上手。
- 部署：ci.sh 一键构建上传，灰度发布。

**【项目案例】** "搭脚手架时最先写哪三个文件？"——答：`utils/common.js`（请求封装）、`utils/directive.js`（权限指令）、`components/myTab`（动态路由壳）。先把**地基三件套**打好，后面业务页面全是填空。这个回答顺序本身就是架构思维的体现。

## 4-17. 讲一次你排查过的疑难 Bug（★★）

**详细回答（口述稿）：**
> "我讲一个排查了两个小时的疑难 bug，用 STAR 结构。背景：货主端订单列表，删除第一行数据后，第二行内嵌的备注输入框内容'串'到了第一行。定位过程：先用二分法——把输入框内容打印出来，发现 DOM 节点被复用了，第一行的输入框节点承载了第二行的值。这是典型的 key 问题：列表用 index 做 key，删掉第一行后 Vue 按 index 复用节点，输入框的内容跟着节点跑了。修复：把 key 从 index 改成业务唯一 id（waybillId），DOM 按身份复用，删除后节点被正确销毁重建，问题消失。事后我做了两件事：一是全项目排查同类写法，把列表 key 全部规范为业务 id；二是组件库文档里加了'列表 key 必须用唯一 id'的约定，并写了 eslint 提示。这个 bug 的启示：框架的复用机制是把双刃剑，理解 diff 的 key 语义，才能避免这类隐蔽问题。"

**答案要点（挑一个有层次感的）：**
- 选材原则：现象 → 假设 → 定位 → 根因 → 修复 → 防复发，六个环节缺一不可；要讲"不是百度一下就会"的问题。
- 示例 A（数据更新不渲染）：订单状态流转后 `order.status` 改了但页面不更新 → 排查发现是**对象新增字段不响应** → `this.$set` 修复 → 规范：动态字段先初始化。根因是 Vue2 defineProperty 局限。
- 示例 B（chunk 加载失败白屏）：用户长时间停留后点菜单白屏，控制台 `Loading chunk failed` → 原因是**版本更新后旧 chunk 被清理**，`router.onError` 捕获 → 提示刷新 + `reload` 兜底。
- 示例 C（弱网丢单）：司机端回单上传失败率 30% → 加**压缩 + 分片 + 断点续传 + 重试队列** → 失败率降到 1%。
- 方法论收尾：善用二分定位（git bisect）、DevTools 堆快照、浏览器 Performance、日志埋点（前端上报 sysLog）。

**【项目案例】** 推荐讲 **B（chunk 失败）**：这是 SaaS 常驻页面 + 频繁发版场景下的高发问题，答案里"`router.onError` + `confirm('系统已更新，是否刷新')` + `location.reload()`"是标准解法，且一听就是真实经历。

## 4-18. Vue2 老项目要不要迁 Vue3？你怎么做技术选型？（★★）

**详细回答（口述稿）：**
> "我的观点很明确：老项目不激进全量迁移，新模块用 Vue3，灰度过渡。为什么不全量迁？老项目 1780 个文件、40+ 组件，迁移成本不只是重写，还有生态依赖（Element UI 2.x 不兼容 Vue3，要换 Element Plus）、构建链、回归测试，风险远大于收益。我的灰度策略是：老平台保持 Vue2.6 稳定，维护为主；新业务（AI 聊天、新看板、新 H5）直接用 Vue3 + Vite 起，Vue3 的响应式、组合式 API 对复杂状态管理更有优势；组件层尽量用跨版本可复用的纯 JS 工具（common.js 这类不依赖框架的）。选型判断标准：业务是否要长期演进？团队是否熟 Vue3？有没有必须用 Vue3 的特性？如果三个都是'否'，Vue2 用着也挺好。技术选型是'算账'不是'追新'，稳定交付优先。"

**答案要点：**
- 评估维度：业务稳定性、团队能力、迁移成本（依赖兼容、语法、测试回归）、收益（性能、TS、生态）。
- 判断：1780 文件的核心平台，全量迁移风险高、收益边际递减 → **不迁移**，用 Vue2.6 继续维护（补 `composition-api` 插件平滑过渡）。
- 新模块/新系统 → 直接 Vue3 + Vite + Pinia + TS。
- **灰度策略**：壳子不动，新功能（AI 聊天、新看板）以独立 Vue3 应用挂载，与老系统共存，逐步证明可行后扩大范围。
- 讲"不迁"的理由比"无脑迁"更显成熟：老系统稳定运行、团队熟练度、5 端联动风险。

**【项目案例】** 公司实际路径：老平台（本项目）Vue2.6 + 新系统 Vue3 双轨并行；aiChat 组件就是 Vue3 的"试验田"——先在 demo 页验证组合式 API + 流式 + 工具调用，再推广到新系统。面试讲"**渐进式演进 + 试点验证**"，体现技术决策的克制与数据驱动。

## 4-19. 你们团队的协作方式与文档建设？（★）

**详细回答（口述稿）：**
> "协作和文档我分三块讲。代码协作：Git 主干 + 功能分支模型，feature 分支开发、code review 后合入，commit 用 commitlint 规范，husky 卡 lint，保证主分支永远可发布。接口协作：接口文档我们做了 api-00 系列，统一了 RPC 接口的 beanName/methodName/参数格式，前端调后端不需要来回对字段名，接口变更先改文档再改代码。知识沉淀：web-README + 25 个模块文档（web-00~25），记录架构设计、组件 API、常见坑；组件库有使用文档，新同学照着文档三天能上手。我的理念：文档不是写完就完，要跟代码一起进 code review；'文档驱动开发'在接口和组件这两块尤其值钱。团队 5-10 人并行开发 5 个端不乱，靠的就是这套协作规则。"

**答案要点：**
- 流程：Git 分支模型（feature → develop → release → tag）+ MR 评审 + lint 门禁。
- 接口协作：前端定义入参出参约定，后端按 beanName/methodName 对齐；接口变更走变更记录。
- 文档：`docs/` 知识库——web-00~25（技术总览、开发规范、组件库、业务域文档、API 索引）+ usr-00~04（用户指南）；API 清单由脚本自动生成（`tools/extract-api.js` 扫 1780 文件提取 1764 接口）。
- 新人 onboarding：开发规范文档 + 组件库示例 + 结对 review 两周上线。
- 提效：接口文档自动化、公共组件沉淀流程（"用两次就提公共组件"原则）。

**【项目案例】** 接口清单脚本是亮点：`extract-api.js` 用正则扫描全项目 `postUrl("bean","method",...)` 调用，自动生成按端 + 业务域分类的 API 索引，**接口变更后跑一次脚本文档即同步**——"文档自动化"代替"人肉维护文档"。面试可顺势讲 AI 辅助写文档的实践。
